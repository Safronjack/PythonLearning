## День 1. TDD и characterization tests

### TDD — это короткий цикл обратной связи

**Test-driven development (TDD)** — способ разрабатывать поведение маленькими циклами:

1. **Red:** написать один тест нового поведения и увидеть ожидаемое падение.
2. **Green:** добавить минимальную реализацию, которая делает этот тест и существующий набор зелёными.
3. **Refactor:** улучшить структуру без изменения публичного поведения; тесты остаются зелёными.

Красный этап полезен только тогда, когда тест падает по ожидаемой причине. `ImportError`, ошибка фикстуры или опечатка в имени не доказывают, что тест способен заметить отсутствие бизнес-правила.

Пример будущего чистого правила:

```python
def calculate_stock_days(quantity: int, average_daily_sales: int) -> int | None:
    """Return full days of stock, or None when demand is zero."""
```

До кода нужно письменно определить policy:

- отрицательные значения недопустимы;
- при нулевом спросе запас не заканчивается, поэтому возвращается `None`;
- дробный остаток дня не считается полным днём.

Test oracle должен происходить из этого контракта, а не копировать внутреннюю формулу функции.

### Characterization test

**Characterization test** фиксирует фактическое важное поведение существующего кода перед изменением. Он отвечает: «Что система делает сейчас?» Это защитная сетка для рефакторинга, а не разрешение объявить любой баг правильным.

Порядок:

1. выбрать рискованный legacy path;
2. проверить требование и решить, поведение верно или ошибочно;
3. для верного поведения добавить тест;
4. для бага сначала описать ожидаемый новый контракт и regression test;
5. изменить структуру маленьким шагом;
6. прогнать targeted и полный наборы.

### Что сохранять в TDD log

- требование и риск;
- имя одного нового теста;
- команда и причина red;
- минимальное изменение green;
- вид рефакторинга;
- результаты targeted и full suite;
- commit hash или diff reference, если работа ведётся в Git.

### Типичные ошибки

- написать реализацию раньше теста и назвать это TDD;
- одновременно добавить пять поведений — причина red становится неясной;
- принять ошибку настройки за red;
- менять test oracle вслед за реализацией;
- рефакторить вместе с изменением behavior;
- запускать только новый тест и не видеть регрессию.

### Самопроверка

1. Почему `ModuleNotFoundError` не является полезным red?
2. Чем characterization test отличается от теста нового требования?
3. Почему на green допустима простая реализация?
4. Что обязано остаться неизменным во время refactor?

Документация: [pytest — assertions](https://docs.pytest.org/en/stable/how-to/assert.html) — как pytest показывает причину падения обычного `assert`.

## День 2. Транзакции и конкуренция

### Обычный database test не всегда видит реальную транзакцию

Django `TestCase` обычно оборачивает test в transaction ради скорости и isolation. Для кода, который проверяет commit, rollback, row locks или конкурирующие transactions, нужен настоящий transaction-enabled test (`transaction=True`/`transactional_db`). Он медленнее, поэтому используется точечно.

SQLite не заменяет PostgreSQL в тесте PostgreSQL locking semantics. Конкурентный сценарий должен выполняться на отдельной test PostgreSQL database.

### Что такое race condition

**Race condition** возникает, когда результат зависит от непредсказуемого порядка параллельных операций.

Пример: на складе одна машина. Два покупателя одновременно читают `quantity=1`, оба уменьшают значение и оба получают успех. Каждый отдельный запрос выглядит корректно, но общий инвариант нарушен.

Полезный конкурентный тест не обязан предсказывать, какой buyer победит. Он проверяет инварианты:

- ровно один успех;
- ровно один контролируемый отказ;
- остаток равен нулю, но не отрицателен;
- создана ровно одна продажа;
- деньги списаны только у победителя;
- не осталось частично изменённых строк.

### Отдельные соединения

Потоки должны выполнять database work через разные соединения. Один connection нельзя бездумно делить между потоками. Worker закрывает старое соединение перед работой, получает собственное и освобождает его после; точная реализация зависит от Django и database adapter текущего проекта.

### Явная синхронизация

`sleep(0.2)` не гарантирует порядок на другой машине. Используйте `threading.Barrier`, `Event` или контролируемую точку внутри test helper:

```python
barrier = threading.Barrier(2)

def worker():
    barrier.wait(timeout=2)
    return try_buy_last_car()
```

Это лишь скелет. Database подготовка должна происходить до запуска workers, а результаты и исключения — собираться безопасно.

### Защита от зависания

- timeout у barrier/event;
- timeout ожидания результата;
- `join()` с ограничением;
- проверка, что threads завершились;
- сбор каждого исключения;
- cleanup соединений в `finally`;
- никакого бесконечного ожидания lock.

### Locks и deadlocks

`SELECT ... FOR UPDATE` удерживает row lock до завершения transaction. Если разные операции блокируют строки в разном порядке, возможен deadlock. Единый порядок блокировок снижает риск. Test должен требовать контролируемого исхода и ограниченного времени, а не зависать.

### Инвариант важнее точного schedule

Планировщик потоков недетерминирован. Если контракт не определяет победителя, assertion `buyer_a succeeds` хрупок. Проверяйте множество разрешённых outcomes и одно обязательное итоговое состояние.

### Самопроверка

1. Почему два последовательных вызова не доказывают безопасность при конкуренции?
2. Зачем workers отдельные database connections?
3. Чем barrier лучше `sleep()`?
4. Какой конечный инвариант важнее имени победителя?

Документация: [pytest-django — database access](https://pytest-django.readthedocs.io/en/latest/database.html) — когда нужны обычный database test и transaction-enabled test.

## День 3. Управляемое время и side effects

### Deterministic test

**Детерминированный тест** при одинаковом коде и данных даёт одинаковый результат. Источники нестабильности:

- текущее время и часовой пояс;
- случайные числа, UUID и токены;
- порядок из неупорядоченного источника;
- реальная сеть, почта или файловая система;
- действие, запланированное после commit;
- глобальное изменяемое состояние.

### Dependency injection вместо глобального времени

Важное правило проще тестировать, если clock передаётся явно:

```python
def is_promotion_active(promotion, *, now):
    return promotion.starts_at <= now < promotion.ends_at
```

Тогда тест проверяет секунду до начала, точное начало, секунду до конца и точный конец. Сначала задайте интервал: здесь `[start, end)`, то есть начало включено, конец исключён.

### Patch where looked up

Если dependency всё же патчится, заменять нужно имя там, где production-модуль его использует. Патч источника часто оставляет уже импортированную ссылку нетронутой. Предпочитайте маленькую явную dependency глобальному monkeypatch.

### Side effect после commit

Email или публикация события не должны происходить, если transaction откатилась. `transaction.on_commit()` позволяет отложить действие до успешного commit. Тесты должны отдельно доказать:

- при commit callback зарегистрирован и выполнен один раз;
- при rollback callback не выполняется;
- повторный application call не дублирует эффект, если контракт требует идемпотентность;
- provider failure превращается в согласованный результат, а не частичную запись.

### Не проверяйте сеть интернетом

Unit/integration tests используют fake/spy на внешней границе. E2E этой недели тоже ограничен локальным сервером. Реальный provider проверяется отдельным sandbox/contract process, если он вообще предусмотрен проектом.

### Время выполнения — не время бизнеса

Не смешивайте:

- business clock (`now`, срок акции);
- monotonic clock для duration/timeout;
- database timestamp;
- локальный часовой пояс разработчика.

Для duration используется monotonic source, потому что системные часы могут измениться.

### Самопроверка

1. Как проверить точный конец акции при полуоткрытом интервале?
2. Почему patching глобального времени может затронуть чужие tests?
3. Что должен доказать rollback scenario для email?
4. Почему реальный HTTP provider делает test ненадёжным?

Документация: [Django — transactions и `on_commit()`](https://docs.djangoproject.com/en/5.2/topics/db/transactions/) — связь commit/rollback с отложенными callbacks.

## День 4. Async-тесты только для async-кода

### Сначала inventory, потом инструмент

`async def` создаёт coroutine. Она выполняется только после `await` или запуска как task. Async test нужен, когда production path действительно асинхронный: async view, async service/client, iterator или task orchestration. Нельзя превращать синхронный код в async ради галочки.

Inventory ищет:

- `async def`, `await`, `async for`, `async with`;
- создание tasks;
- async HTTP/database adapters;
- sync↔async bridges;
- заявленный ASGI path.

### Две допустимые ветки дня

**Ветка A: async-код есть.** Выбрать встроенные Django/unittest средства или совместимый `pytest-asyncio`; проверить success, exception, cancellation/timeout, sync boundary и отсутствие pending tasks.

**Ветка B: async-кода нет.** Записать команды inventory и найденные результаты, объяснить, почему async dependency не нужна, и проверить одну реальную синхронную границу. Все шесть scenario IDs получают статус `N/A with evidence`, а не `passed`.

### Что проверяет async test

- coroutine действительно awaited;
- исключение не теряется в background task;
- timeout/отмена обрабатываются согласно contract;
- resources закрываются;
- event loop не содержит утёкших tasks;
- синхронный ORM не блокирует async path или вызван через поддерживаемую границу;
- нет зависимости от случайного порядка scheduling.

### `AsyncMock`

Async dependency заменяется async-compatible double. Обычный `Mock` может дать ложный интерфейс: его нельзя корректно `await`. Проверяется не только `called`, но и `awaited` с ожидаемыми arguments.

### Самопроверка

1. Почему наличие ASGI settings ещё не доказывает наличие async business path?
2. Чем вызов coroutine отличается от её выполнения?
3. Как test обнаруживает потерянное исключение background task?
4. Когда `pytest-asyncio` не нужно устанавливать?

Документация: [Django — testing asynchronous code](https://docs.djangoproject.com/en/5.2/topics/testing/tools/#testing-asynchronous-code) — поддерживаемые способы вызывать async views и async test methods.

## День 5. Live-server end-to-end flows

### Что меняется в E2E

API test может вызывать DRF test client внутри процесса. Live-server E2E отправляет настоящий локальный HTTP request на поднятый test server и проходит routing, middleware, authentication и response serialization ближе к реальному клиенту.

E2E дорогой и диагностирует хуже, поэтому тестируются несколько наиболее ценных потоков, а не все комбинации.

### Хороший E2E flow

```text
начальное состояние
→ HTTP register
→ безопасно получить test verification token
→ HTTP verify
→ HTTP obtain JWT
→ HTTP create offer
→ HTTP read/cancel own offer
→ проверить response и итоговую database
```

Token нельзя вынимать из production log. В test environment допустим контролируемый mail outbox или test-only adapter, не доступный в production.

### Изоляция

- только автоматически созданная test database;
- local ephemeral port из fixture/live server;
- никакой общей учётной записи;
- уникальные deterministic данные;
- cleanup после падения;
- timeout каждого HTTP request;
- запрет внешней сети;
- никакой зависимости от порядка E2E tests.

### Что утверждать

На каждом ключевом шаге:

- status code;
- минимальный response contract;
- security property, например отсутствие чужих данных;
- итоговое database state;
- нужный side effect и отсутствие запрещённого.

Один финальный `assert status == 200` не объясняет, на каком этапе сломался flow.

### Самопроверка

1. Какой дополнительный слой доказывает live-server test относительно APIClient?
2. Почему E2E-набор должен быть небольшим?
3. Откуда безопасно взять verification token в test environment?
4. Что проверить кроме HTTP status?

Документация: [Django — `LiveServerTestCase`](https://docs.djangoproject.com/en/5.2/topics/testing/tools/#liveservertestcase) — поднятие локального сервера с test database.

## День 6. Flaky-, order- и time-dependent tests

### Flaky test — сигнал, а не неудобство

**Flaky test** иногда проходит, иногда падает без соответствующего изменения продукта. Причина может быть:

- дефектом самого теста;
- настоящей race condition продукта;
- shared state и зависимостью от порядка;
- временем/часовым поясом;
- случайными данными;
- внешней сетью;
- слишком жёстким performance threshold;
- исчерпанием ресурсов.

Автоматический retry снижает видимость проблемы и не является исправлением.

### Диагностический протокол

1. сохранить node ID, seed, timezone, locale, Python/Django/PostgreSQL versions;
2. запустить test отдельно много раз;
3. запустить вместе с ближайшей группой;
4. поменять порядок групп явно;
5. искать shared mutable state, кэш, незакрытые connections/tasks;
6. заменить время/random на controlled inputs;
7. проверить, не обнаружен ли реальный product race;
8. исправить причину и повторить clean runs.

### Order dependence

Если `test_b` проходит только после `test_a`, один из них оставляет или ожидает состояние. Каждый test должен самостоятельно организовать необходимые данные. Нельзя «починить» проблему закреплением удобного порядка.

### Performance и N+1

Секундный порог зависит от нагрузки машины. Для ORM list endpoint надёжнее query-count budget на фиксированном наборе данных. Сравните малый и увеличенный набор: количество запросов не должно расти на одну/несколько операций для каждой строки.

Duration можно использовать как грубый ограничитель зависания, но не как единственное доказательство производительности.

### Quarantine

Временно изолировать test допустимо только с owner, причиной, issue и сроком. Критический security/data-integrity test нельзя молча убрать из gate. `xfail`/skip не должны превращаться в кладбище неизвестных проблем.

### Самопроверка

1. Почему десять успешных повторов не доказывают отсутствие race condition?
2. Как отличить product race от test pollution?
3. Чем query budget устойчивее точного времени?
4. Какие данные нужны, чтобы воспроизвести flaky failure?

Документация: [pytest — Flaky tests](https://docs.pytest.org/en/stable/explanation/flaky.html) — систематизация причин и мер против нестабильности.

## День 7. Quality gate и regression strategy

### Quality gate

**Quality gate** — однозначный набор проверок, который должен пройти до принятия изменения. Это не одна гигантская команда без структуры. Быстрый feedback идёт первым, дорогой — позже:

```text
configuration/collection
→ unit
→ integration/API
→ transaction/concurrency
→ E2E
→ coverage/report checks
```

Каждый локальный и CI command документируется одинаково. Gate завершает процесс ненулевым exit code при обязательном падении и отдельно показывает skipped/xfail.

### Regression map

Для каждого критического инварианта записываются:

- риск и business owner;
- positive test;
- negative/boundary test;
- самый низкий достаточный уровень;
- более высокий test, если он доказывает wiring;
- side effects и rollback;
- место запуска в gate;
- пробел/будущий контракт.

Особый случай: повтор Celery-задачи важен, но Celery ещё не изучен. В карте фиксируется будущий контракт идемпотентности и ожидаемые состояния; test реализуется на неделях 18–19.

### Coverage как вопрос

Branch report помогает спросить: «Почему эта ветка не выполнена?» Допустимые ответы:

- риск уже доказан другим уровнем;
- defensive/unreachable branch документирована;
- исключён generated/framework code;
- найден реальный пробел и добавлен meaningful test.

Недопустимый ответ: добавить test, который вызывает строку без проверки поведения.

### Финальная защита

Ученик должен уметь для выбранного теста объяснить:

1. какой риск он закрывает;
2. почему выбран этот уровень;
3. что является oracle;
4. какие реальные и заменённые dependencies используются;
5. как test мог бы дать false positive;
6. какое изменение production code сделает его red;
7. почему test воспроизводим;
8. чего этот test не доказывает.

### Самопроверка

1. Почему один E2E не заменяет unit и integration tests?
2. В каком порядке запускать быстрые и дорогие группы?
3. Как учитывать будущий Celery contract, не имитируя изученный инструмент?
4. Что важнее: 100% coverage или доказательство критических ветвей?

Документация: [coverage.py — branch coverage](https://coverage.readthedocs.io/en/latest/branch.html) — поиск выполненных и пропущенных ветвей управления.

## Словарь недели

- **TDD** — разработка короткими циклами red-green-refactor.
- **Characterization test** — тест принятого текущего поведения перед изменением.
- **Race condition** — зависимость результата от порядка параллельных событий.
- **Invariant** — условие, которое обязано сохраняться при любом разрешённом порядке.
- **Lock** — временное ограничение конкурентного доступа к данным.
- **Deadlock** — взаимное ожидание locks без прогресса.
- **Deterministic test** — тест с воспроизводимым результатом при одинаковых входах.
- **Side effect** — изменение вне возвращаемого значения: database, email, HTTP, file и т. п.
- **Coroutine** — результат вызова `async def`, который нужно выполнить через `await`/event loop.
- **E2E** — проверка целого пользовательского пути через реальные системные границы.
- **Flaky test** — тест с меняющимся результатом без соответствующего изменения продукта.
- **Quality gate** — обязательный воспроизводимый набор проверок перед принятием изменения.

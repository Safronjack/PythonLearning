## Правила сдачи

После активации выполняй один день и пиши: `Проверь день N недели 3`. Агент читает и запускает код, не изменяя его, затем обновляет `ASSESSMENT.md`.

Общие требования:

- использовать только стандартную библиотеку;
- хранить деньги в `Decimal`, созданном из строки;
- давать классам, методам и переменным понятные английские имена;
- указывать аннотации публичных методов и функций;
- защищать заявленные инварианты;
- не использовать изменяемые атрибуты класса для состояния экземпляров;
- не читать `input()` и не печатать из бизнес-моделей;
- добавлять `assert` для чистого и предсказуемого поведения;
- не скрывать неожиданные исключения;
- не применять неизвестный паттерн или магический метод без объяснения;
- заполнять самооценку в конце каждого файла.

До дня 6 достаточно запуска Python и инспекций PyCharm. Устанавливать mypy или другие зависимости специально для этой недели не нужно.

## День 1. Классы, экземпляры, атрибуты и методы

Файл: `day_01_classes_objects.py`.

Теория: главы 1–5 и прогнозы 1–3.

### 1. Словарь и объект

Создай словарь автомобиля с `vin`, `brand`, `model` и `price`. Затем создай класс `Car` с теми же данными. В комментарии объясни:

- что является классом;
- что является экземпляром;
- где хранится состояние;
- какое поведение удобнее перенести в метод.

### 2. Инициализация

Реализуй `Car.__init__` с полями:

```text
vin: str
brand: str
model: str
price: Decimal
```

VIN, марка и модель не могут быть пустыми после `strip()`. Цена должна быть положительной. Для нарушений вызывай `ValueError` с понятной причиной.

### 3. Поведение экземпляра

Добавь методы:

```text
describe() -> str
calculate_total(quantity: int) -> Decimal
change_price(new_price: Decimal) -> None
```

Количество и новая цена должны быть положительными. Методы ничего не печатают.

### 4. Независимость экземпляров

Создай минимум два автомобиля. Измени цену только первого и через `assert` докажи, что второй не изменился.

### 5. Атрибут класса

Добавь неизменяемый по смыслу class attribute `category = "vehicle"`. Покажи поиск через класс и экземпляр. Затем создай одноимённый instance attribute и объясни затенение, не меняя `Car.category`.

### 6. Общий изменяемый атрибут

На отдельном учебном классе `BrokenInventory` воспроизведи общий список как атрибут класса. После наблюдения создай правильный `Inventory`, где новый список появляется в `__init__`.

Ошибка должна остаться только в изолированном демонстрационном блоке и не использоваться основной моделью.

### 7. Identity, type и namespace

Для двух объектов проверь:

- `first_car is second_car`;
- `type(first_car)`;
- `isinstance(first_car, Car)`;
- `vars(first_car)`.

Не сравнивай численные результаты `id()` между запусками.

### 8. Проверки

Добавь минимум 10 `assert`: создание, описание, расчёт одной и нескольких единиц, смена цены, независимость объектов и ошибки для каждого недопустимого поля.

Для проверки ожидаемого исключения пока используй маленький `try`/`except ValueError` с флагом или вспомогательной функцией из пройденного материала.

### Обязательные сценарии

1. Корректный автомобиль и количество 1.
2. Количество 3.
3. Пустой VIN.
4. Марка из пробелов.
5. Пустая модель.
6. Цена `0`.
7. Отрицательная цена.
8. Количество `0`.
9. Изменение цены одного из двух объектов.
10. Два `Inventory` не разделяют списки.

Критерий: объект валиден сразу после создания, состояние экземпляров независимо, расчёт возвращает `Decimal`, а `self` объясняется как конкретный экземпляр.

## День 2. Инкапсуляция, свойства и виды методов

Файл: `day_02_encapsulation_properties.py`.

Теория: главы 5–8 и прогноз 4.

### 1. Покупатель и баланс

Создай `Customer`:

```text
customer_id: int
name: str
_balance: Decimal
email_confirmed: bool
```

Положительный id и непустое имя проверяются в `__init__`. Начальный баланс не может быть отрицательным.

### 2. Read-only property

Предоставь `balance` как property без публичного setter. Внешний код читает баланс, но меняет его только методами:

```text
deposit(amount) -> None
withdraw(amount) -> None
```

Сумма операции положительна. Списание сверх баланса запрещено. После отказа баланс не изменяется.

### 3. Вычисляемое property

Добавь property `can_receive_offers`, которое возвращает `True`, только если email подтверждён. Оно не должно менять объект.

### 4. Проверяемый setter

На отдельном классе `CarListing` реализуй property `price` с проверкой положительного `Decimal`. И `__init__`, и последующая запись обязаны использовать одно правило.

### 5. Instance method

Добавь покупателю метод `confirm_email()`. Покажи, что он работает с конкретным экземпляром и не меняет другого покупателя.

### 6. Class method

Реализуй `Customer.from_dict(data)`. Он создаёт объект через `cls`, явно извлекает обязательные значения и не изменяет входной словарь.

Неверная внешняя структура может вызвать `KeyError` или вашу понятную ошибку — выбери контракт и запиши его в docstring.

### 7. Static method

Добавь `Customer.is_valid_name(value) -> bool` либо обоснуй обычную функцию модуля. Метод не должен читать состояние экземпляра или класса.

### 8. `_name`, `__name` и `__name__`

На маленьком отдельном классе покажи name mangling для `__value` через `vars()`. В комментарии объясни, почему это не защита секрета. Не изменяй mangled-имя снаружи.

### Обязательные сценарии

1. Начальный баланс `0` разрешён.
2. Отрицательный начальный баланс запрещён.
3. Пополнение на `100.00`.
4. Списание всей суммы оставляет `0`.
5. Списание больше баланса отвергается без изменения.
6. Нулевая и отрицательная операция запрещены.
7. Прямая запись в read-only `balance` отвергается.
8. Цена listing не может стать нулевой.
9. `from_dict` создаёт независимый объект и не меняет dict.
10. Подтверждение email одного покупателя не влияет на другого.

Критерий: публичные операции сохраняют инварианты, property используется по смыслу, а различия трёх видов методов объяснимы.

## День 3. Композиция, наследование, полиморфизм и ABC

Файл: `day_03_relationships_polymorphism.py`.

Теория: главы 9–12 и 19.

### 1. Композиция склада

Создай `Inventory`, который внутри хранит автомобили и предоставляет только необходимые операции:

```text
add(car) -> None
find_by_vin(vin) -> Car | None
remove_by_vin(vin) -> Car
count() -> int
```

Повторный VIN запрещён. `remove_by_vin` для неизвестного VIN вызывает понятный `ValueError`. Не наследуй `Inventory` от list и не возвращай внутренний список напрямую.

### 2. Композиция автосалона

`Dealership` получает имя и создаёт собственный `Inventory`. Докажи, что склады двух автосалонов независимы.

### 3. Агрегация поставщика

Создай `Supplier` и передай готовый объект в `Dealership.add_supplier(supplier)`. Один поставщик может сотрудничать с двумя автосалонами. В комментарии объясни, почему поставщик не обязан исчезнуть вместе с автосалоном.

### 4. Корректное наследование

Создай абстрактный `Vehicle` с общими `vin`, `brand`, `model` и abstract method `get_usage_description() -> str`.

Реализуй два наследника:

- `PassengerCar`;
- `CommercialVan`.

Каждый возвращает своё описание назначения и сохраняет контракт результата.

### 5. Полиморфный обход

Напиши функцию, которая принимает коллекцию `Vehicle`, вызывает у каждого `get_usage_description()` и возвращает список строк. В ней запрещены проверки точного типа и ветки по имени класса.

### 6. ABC

Проверь, что создать голый `Vehicle` нельзя. Ошибочный вызов оставь в контролируемом `try`/`except TypeError` и объясни роль `@abstractmethod`.

### 7. Duck typing

Создай отдельный класс, который не наследуется от `Vehicle`, но имеет совместимый метод описания. Покажи работу маленькой функции с этим объектом и объясни отличие duck typing от общей номинальной иерархии.

### 8. Выбор отношения

Для каждой пары письменно выбери композицию, агрегацию, наследование или простую ассоциацию:

- автосалон и склад;
- автосалон и поставщик;
- легковой автомобиль и транспортное средство;
- сервис покупки и чек;
- автомобиль и список.

### Обязательные сценарии

1. Добавление и поиск автомобиля.
2. Неизвестный VIN возвращает `None` при поиске.
3. Повторный VIN отвергается без дубликата.
4. Удаление существующего и неизвестного VIN.
5. Склады двух автосалонов независимы.
6. Один Supplier используется двумя Dealership.
7. Два наследника дают разные описания через один вызов.
8. Абстрактный класс нельзя создать.
9. Полиморфная функция не проверяет конкретные типы.

Критерий: отношение «является» не путается с «содержит», базовый контракт не ломается, а полиморфизм уменьшает ветвление.

## День 4. Dataclass, Enum и магические методы

Файл: `day_04_dataclasses_enums_magic.py`.

Теория: главы 13–17 и прогнозы 5–7.

### 1. Enum статуса

Создай `CarStatus` со значениями `AVAILABLE`, `RESERVED`, `SOLD`. Покажи `.name`, `.value`, преобразование корректной строки и контролируемый `ValueError` для неизвестной строки.

В основной модели сравнивай значения Enum, а не случайные строки.

### 2. Обычный dataclass

Создай `CarListing` с `vin`, `model`, `price`, `status`. Через `__post_init__` проверь непустой текст и положительный `Decimal`.

Сравни два экземпляра с одинаковыми полями через `==` и `is`.

### 3. `default_factory`

Создай dataclass `DealershipSnapshot` с независимым списком VIN. Два экземпляра не должны делить список.

### 4. Frozen value object

Создай `SaleReceipt` с `sale_id`, `vin`, `subtotal`, `discount`, `total`. Используй `frozen=True`; в `__post_init__` проверь согласованность сумм и неотрицательный итог.

Покажи, что обычная запись в поле после создания запрещена.

### 5. `__repr__` и `__str__`

На обычном классе `Customer` реализуй:

- `__repr__` для разработчика с однозначными полями без чувствительных данных;
- `__str__` для пользователя.

Проверь отдельный объект и список объектов: список использует `repr` элементов.

### 6. `__eq__`

Считай покупателей равными по устойчивому `customer_id`. Метод принимает `other: object` и возвращает `NotImplemented` для другого типа. Проверь равенство, неравенство и сравнение с целым числом.

Не добавляй искусственный `__hash__` изменяемому Customer.

### 7. Контейнерный протокол

Создай `Inventory` с:

```text
__len__
__iter__
__contains__
```

Проверь `len(inventory)`, цикл и вхождение автомобиля. Изменение выполняется обычным публичным методом `add`, а не магическим методом.

### 8. Контракт hash

Создай маленький `@dataclass(frozen=True) Vin`. Два равных VIN должны иметь одинаковый hash и схлопываться в set. В комментарии объясни, почему mutable `Customer` не нужно насильно делать hashable.

### 9. Метаклассы и дескрипторы — наблюдение

Выведи `type(CarListing)`. Затем создай отдельный маленький `PriceHolder` с property, изучи `type(PriceHolder.price)` и посмотри наличие `__get__`/`__set__` у объекта property. Объясни на уровне этой недели, почему чтение атрибута может запускать поведение.

Не создавай собственный метакласс или дескриптор: это обзорный эксперимент, а не задача на реализацию.

### Обязательные сценарии

1. Все три статуса и корректное преобразование из строки.
2. Неизвестный статус.
3. Равные по полям dataclass-объекты, но разная identity.
4. Два независимых списка `default_factory`.
5. Корректный frozen receipt.
6. Несогласованные `subtotal - discount != total`.
7. `repr` и `str` различаются по назначению.
8. Customer сравнивается с Customer и другим типом.
9. Пустой и непустой Inventory.
10. Равные frozen VIN работают в set.
11. Класс является объектом, а property участвует в дескрипторном протоколе.

Критерий: автогенерация dataclass понятна, Enum защищает состояние, магические методы реализуют естественный протокол и не ломают равенство/хеширование.

## День 5. MRO, `super()` и осторожное наследование

Файл: `day_05_mro_super.py`.

Теория: главы 18–19 и прогноз 8.

### 1. Простое наследование

Создай `Vehicle` с инициализацией VIN и `PassengerCar`, который добавляет число мест. Вызови `super().__init__()` и проверь, что оба атрибута созданы.

### 2. Переопределение с расширением

Базовый `describe()` возвращает общую строку. Наследник использует `super().describe()` и добавляет свою часть, сохраняя тип результата.

### 3. Чтение MRO

Создай ромб:

```text
Base
├── InventoryLoggingMixin
└── ValidationMixin
    \ /
  ManagedInventory
```

Точное расположение базовых классов запиши в коде. До запуска предскажи `ManagedInventory.mro()`, затем сравни с результатом.

### 4. Cooperative `super()`

Каждый класс цепочки реализует одноимённый метод, записывает своё имя в новый список и передаёт выполнение дальше через `super()`. Каждый участник должен встретиться один раз.

Не вызывай базовый класс напрямую по имени.

### 5. Порядок базовых классов

Создай второй класс с обратным порядком mixin и сравни MRO и результат. Объясни, почему перестановка базовых классов изменяет поведение.

### 6. Совместимый контракт

Покажи корректное переопределение метода расчёта комиссии. Отдельно в комментарии приведи плохой пример, где наследник требует больше обязательных параметров или возвращает другой тип.

### 7. Mixin

Создай небольшой `AuditMixin`, добавляющий форматированное audit-сообщение. Он не читает ввод, не пишет файл и не хранит глобальный журнал.

### 8. Рефакторинг к композиции

Возьми намеренно сомнительную модель `Dealership(list)` или `PurchaseService(dict)` и перепиши её через поле-коллекцию. В комментарии объясни отсутствующее отношение «является».

### Обязательные сценарии

1. Наследник полностью инициализирован.
2. `describe()` сохраняет базовую и добавляет дочернюю информацию.
3. MRO предсказан до запуска.
4. В ромбе общий базовый метод вызывается один раз.
5. Обратный порядок mixin наблюдаемо меняет цепочку.
6. Переопределённый метод сохраняет входной и выходной контракт.
7. Mixin решает одну маленькую задачу.
8. Итоговый Dealership не наследуется от встроенной коллекции.

Критерий: ученик читает MRO, объясняет `super()` как продолжение поиска по MRO и предпочитает композицию необоснованному наследованию.

## День 6. Typing, Protocol, SOLID и dependency injection

Файл: `day_06_typing_solid_di.py`.

Теория: главы 20–25 и прогнозы 9–10.

### 1. Полная типизация небольшой модели

Создай простые `Car`, `Customer` и `SaleReceipt` либо переиспользуй понятия без копирования готового решения. Аннотируй:

- поля;
- параметры;
- возвращаемые значения;
- методы, возвращающие `None`.

Аннотации должны совпадать с runtime-поведением.

### 2. Optional-result

Реализуй `find_car(vin: str) -> Car | None`. В вызывающем коде явно обработай `None` до обращения к автомобилю.

### 3. Абстрактный тип коллекции

Функция `calculate_inventory_value` принимает `Iterable[Car]`, а не только list. Проверь её на list, tuple и generator.

### 4. Callable

Опиши type alias для функции-уведомителя `Callable[[str], None]`. Передай console-функцию и функцию, сохраняющую сообщения в список. Бизнес-операция не должна знать, какая реализация выбрана.

### 5. Protocol политики скидки

Определи `DiscountPolicy` с одним методом. Реализуй минимум:

- `NoDiscountPolicy`;
- `PercentageDiscountPolicy` с проверкой диапазона 0–100.

Обе реализации возвращают сумму скидки `Decimal`, не итоговую цену.

### 6. Dependency injection

`PurchaseService` получает policy и notifier через конструктор. Он не создаёт конкретную policy внутри метода и не обращается к глобальной переменной.

Для учебного сценария сервис вычисляет subtotal, discount и total, проверяет достаточность денег и возвращает `SaleReceipt`. До финального дня можно не менять Car/Customer.

### 7. Fake dependency

Создай маленький fake notifier или замыкание, которое сохраняет сообщения. Через `assert` проверь, что при успехе отправлено одно уведомление, а при отклонении — выбрано и документировано ожидаемое поведение.

### 8. SOLID-аудит

Письменно ответь рядом с кодом:

- какая ответственность у `PurchaseService`;
- как добавить новую discount policy без изменения сервиса;
- какой контракт нельзя ломать реализациям policy;
- почему маленький Protocol лучше огромного интерфейса здесь;
- от какой конкретной реализации сервис больше не зависит.

### 9. Статическая проверка

Используй встроенные инспекции PyCharm. Если type checker уже установлен, можно дополнительно запустить его, но установка не требуется. Не подавляй предупреждения через `Any` или `# type: ignore` без письменного объяснения.

### Обязательные сценарии

1. Поиск существующего и неизвестного VIN.
2. Расчёт для list, tuple и generator.
3. Нулевая скидка.
4. Скидка 10%.
5. Границы 0 и 100 разрешены.
6. Проценты за границами запрещены.
7. Баланс точно равен total.
8. Недостаточный баланс.
9. Подмена notifier без изменения сервиса.
10. Подмена policy без изменения сервиса.

Критерий: аннотации честны, `None` обработан, Protocol описывает минимальный контракт, а зависимости видны в конструкторе.

## День 7. Итоговый проект «Предметная модель автосалона»

Каталог: `day_07_dealership_domain/`.

Теория: главы 23–28 и повтор остальных глав.

### Назначение

Создать чистую Python-модель части будущего Django-проекта. Она хранит объекты в памяти и моделирует продажу одного автомобиля покупателю. Django, БД, HTTP, CLI-ввод и внешние библиотеки пока не используются.

### Структура

```text
day_07_dealership_domain/
├── __init__.py
├── enums.py
├── errors.py
├── contracts.py
├── models.py
├── policies.py
├── services.py
└── main.py
```

### `enums.py`

Определи `CarStatus`:

- `AVAILABLE`;
- `RESERVED`;
- `SOLD`.

### `errors.py`

Создай одну базовую бизнес-ошибку и понятные дочерние ошибки минимум для:

- неподтверждённого email;
- недоступного автомобиля;
- недостаточного баланса;
- дублирующегося VIN;
- неизвестного VIN;
- недопустимой скидки.

Не создавай отдельный класс для каждой возможной строки без смысла. Все ошибки должны сохранять понятное сообщение.

### `contracts.py`

Определи Protocol `DiscountPolicy`:

```text
calculate_discount(subtotal: Decimal) -> Decimal
```

Результат всегда от `0` до `subtotal` включительно.

### `models.py`

`Car`:

- `vin`, `brand`, `model`, `price`, `status`;
- непустые строки и положительная цена;
- новый автомобиль по умолчанию доступен;
- методы смены статуса защищают переходы `AVAILABLE → RESERVED`, `RESERVED → AVAILABLE` и `AVAILABLE/RESERVED → SOLD`;
- статус `SOLD` является конечным: из него нельзя вернуться или продать автомобиль повторно;
- понятные `__repr__` и `__str__` без секретов;
- равенство определяется осознанно и объяснено.

`Customer`:

- положительный `customer_id`;
- непустое имя;
- неотрицательный приватный баланс с read-only property;
- статус подтверждения email;
- `confirm_email`, `deposit`, `withdraw`;
- не допускает отрицательного баланса.

`Supplier`:

- положительный `supplier_id`;
- непустое имя;
- может существовать независимо от автосалона.

`Inventory`:

- приватная коллекция автомобилей;
- уникальность VIN;
- добавление и поиск;
- `__len__`, `__iter__`, `__contains__`;
- внешний код не получает изменяемый внутренний список.

`Dealership`:

- положительный `dealership_id` и непустое имя;
- композиция с собственным `Inventory`;
- агрегация поставщиков без дублирования их id.

`SaleReceipt`:

- frozen dataclass;
- `sale_id`, id автосалона и покупателя, VIN;
- `subtotal`, `discount`, `total`;
- проверяет `subtotal - discount == total` и неотрицательные суммы.

### `policies.py`

Реализуй:

- `NoDiscountPolicy`;
- `PercentageDiscountPolicy`.

Процент — целое число от 0 до 100. Денежный результат округляется до двух знаков по явно указанному правилу `Decimal`.

### `services.py`

`PurchaseService` получает `DiscountPolicy` через constructor injection.

Метод покупки принимает готовые объекты, а не словари и не пользовательский ввод. Он должен:

1. найти автомобиль в нужном автосалоне;
2. проверить подтверждение email;
3. проверить статус автомобиля;
4. рассчитать subtotal, discount и total;
5. проверить достаточность баланса;
6. только после всех проверок списать деньги и отметить автомобиль проданным;
7. вернуть `SaleReceipt`.

При любой ожидаемой ошибке до изменения состояния баланс и автомобиль остаются прежними. Повторная продажа того же VIN запрещена.

Генерацию `sale_id` сделай простейшим явно объяснённым способом внутри памяти. Не используй случайность как гарантию уникальности. Ограничения такого решения запиши в комментарии — позднее id будет выдавать база данных.

### `main.py`

Это точка сборки и демонстрации:

- создаёт автосалон, поставщика, автомобили и покупателя;
- выбирает конкретную discount policy;
- создаёт `PurchaseService`;
- выполняет один успешный сценарий;
- печатает receipt и конечное состояние;
- запускается только под `if __name__ == "__main__"`.

Импорт любого модуля пакета не должен печатать, читать ввод или выполнять продажу.

### Обязательные сценарии

Проверь через `assert` или маленькие проверочные функции:

1. Корректное создание всех моделей.
2. Пустые имена и неположительные id отвергаются.
3. Нулевая/отрицательная цена запрещена.
4. Два автосалона имеют независимые склады.
5. Один Supplier может быть связан с двумя Dealership.
6. Повторный VIN не добавляется.
7. Поиск неизвестного VIN даёт ожидаемую ошибку или `None` согласно контракту.
8. Успешная покупка без скидки.
9. Успешная покупка со скидкой 10%.
10. Баланс точно равен total и становится нулём.
11. Неподтверждённый email: состояние не меняется.
12. Недостаточно денег: состояние не меняется.
13. Автомобиль `RESERVED`: состояние не меняется.
14. Автомобиль `SOLD`: повторная продажа запрещена.
15. Скидка 0% и 100%.
16. Скидка меньше 0 или больше 100.
17. `subtotal - discount == total` у каждого receipt.
18. Два равных по выбранному правилу объекта сравниваются предсказуемо.
19. `len`, цикл и `in` работают для Inventory.
20. Импорт пакета и модулей не запускает demo.

### Архитектурные ограничения

- только стандартная библиотека;
- без Django, базы данных и файлового хранения;
- без `float` для денег;
- без `input()` в моделях и сервисах;
- без `print()` вне `main.py`;

- без циклических импортов;
- без скрытого создания конкретной discount policy внутри сервиса;
- без частичного изменения состояния при отказе;
- без метаклассов и собственных дескрипторов.

### Критерий приёмки

- структура пакета соблюдена;

## Правила сдачи

После активации выполняй один день и пиши: `Проверь день N недели 4`. Агент проверяет код без его изменения и обновляет `ASSESSMENT.md`.

Общие требования:

- использовать только стандартную библиотеку;
- сначала проверять корректность, затем измерять скорость;
- для каждого алгоритма указывать временную и дополнительную пространственную сложность;
- явно писать, изменяет ли функция вход;
- добавлять `assert` для обычных и граничных случаев;
- не использовать встроенную готовую операцию, если задача требует реализовать алгоритм;
- в прикладном коде предпочитать стандартную библиотеку учебной реализации;
- не делать жёстких тестов вида «обязательно быстрее X секунд»;
- не запускать потоки, процессы или event loop при импорте;
- наблюдать и сохранять ошибки worker;
- заполнять самооценку и результаты измерений.

Алгоритмический набор содержит E01–E25 уровня easy и M01–M05 уровня medium. Все easy обязательны. Из medium обязательны любые три; остальные две рекомендуются после исправления основных ошибок.

## День 1. Big O, измерения и поиск

### Документация

- [Модуль `timeit`](https://docs.python.org/3/library/timeit.html) — корректное измерение времени выполнения небольших фрагментов кода.
- [Модуль `bisect`](https://docs.python.org/3/library/bisect.html) — двоичный поиск позиции в отсортированной последовательности.

Файл: `day_01_complexity_search.py`.

### Паспорт дня

- **Цель:** решать базовые задачи обхода и поиска и связывать реализацию с оценкой времени и памяти.
- **Результат:** таблица контрактов E01–E08, рабочие функции, проверки границ и небольшой эксперимент роста времени.
- **Порядок:** для каждой функции сначала заполни строку таблицы; реализуй задачи линейного обхода; затем бинарный поиск; после корректности измерь несколько размеров входа и объясни тенденцию.
- **Готово, если:** известны результаты для пустого списка, отсутствующей цели и дублей; binary search получает отсортированный вход; Big O объясняется числом операций, а не только буквой; измерения не выдаются за точное доказательство.
- **Пример поведения:** линейный поиск возвращает согласованный признак отсутствия, а бинарный — корректный индекс существующего элемента.
- **Обязательно:** E01–E08, таблица и эксперимент. **Рекомендация:** сначала писать простой корректный вариант, затем обсуждать оптимизацию.

### E02. Сумма цен вручную

Посчитай сумму списка целых цен без `sum()`. Не изменяй вход.

### E03. Минимум вручную

Верни первое значение, которое встретилось повторно при движении слева направо, либо `None`. Используй set и объясни ожидаемое `O(n)` время и `O(n)` память.

### E05. Разворот без `reversed()`

Верни новый список в обратном порядке без `reversed()` и `.reverse()`. Исходный список не меняется.

### E06. Линейный поиск

Реализуй поиск индекса первого target. Не используй `.index()`.

Проверь target в начале, середине, конце, отсутствие и дубликаты.

### E07. Все позиции

Верни список всех индексов target. Учти, что размер результата `k` влияет на дополнительную память.

### E08. Бинарный поиск

Реализуй итеративный binary search по отсортированному `list[int]`. Возвращай любой найденный индекс или `None`. Не сортируй внутри функции.

Проверь:

- пустой список;
- один элемент — найден и не найден;
- первый и последний элементы;
- чётную и нечётную длину;
- отсутствующее значение между существующими;
- значение меньше минимума и больше максимума;
- дубликаты.

Отдельно покажи, что применение к несортированным данным нарушает предусловие и результат больше не гарантирован.

### Эксперимент роста

Сравни линейный и бинарный поиск на нескольких размерах, например 100, 1_000, 10_000 и 100_000. Используй несколько повторов. Не включай создание и сортировку данных в замер самого поиска.

Запиши:

- где находится target;
- число повторов;
- измеренные времена;
- почему цифры сами по себе не доказывают Big O;
- почему подготовка сортировки может быть дороже одного линейного поиска.

### Критерий приёмки

- E01–E08 корректны;
- функции имеют ясный контракт;
- binary search всегда уменьшает диапазон;
- предусловие сортировки названо;
- лучший и худший случаи не смешаны;
- измерение отделено от подготовки данных;
- таблица сложности заполнена.

## День 2. Стек, очередь, heap, дерево и простые сортировки

### Документация

- [`collections.deque`](https://docs.python.org/3/library/collections.html#collections.deque) — эффективная реализация очереди и стека.
- [Модуль `heapq`](https://docs.python.org/3/library/heapq.html) — очередь с приоритетом на основе кучи.

Файл: `day_02_structures_sorts.py`.

### Паспорт дня

- **Цель:** выбрать структуру данных по требуемому порядку извлечения и понять механику трёх простых сортировок.
- **Результат:** задачи E09–E18 со стеком, deque, heap, обходами дерева и сортировками, которые можно проверить отдельно.
- **Порядок:** реализуй LIFO-задачи; затем FIFO и ограниченную историю; после этого heap; нарисуй дерево и выполни DFS/BFS; последними напиши три сортировки.
- **Готово, если:** пустые структуры обрабатываются по контракту; heap возвращает три минимума в ожидаемом порядке; DFS/BFS дают предсказанные последовательности; сортировки работают на пустом, одном и повторяющихся элементах.
- **Пример поведения:** одно дерево даёт разные, заранее записанные порядки обхода DFS и BFS.
- **Обязательно:** E09–E18 и сценарии. **Рекомендация:** печатать промежуточные проходы сортировки только во время отладки.

Теория: главы 10–17 и прогноз 5.

### E09. Стек операций

Реализуй отмену последнего действия через list как stack. Поддержи `push`, `peek`, `pop` на уровне небольших функций или класса. Для пустого стека зафиксируй поведение.

### E10. Сбалансированные скобки

Проверь строку из `()[]{}` через stack. Любой закрывающий символ должен соответствовать последнему незакрытому. Остальные символы можно игнорировать или запретить — зафиксируй контракт.

Проверь `""`, `"()"`, `"([])"`, `"([)]"`, `"(("`, `"]"`.

### E11. FIFO-очередь

Через `collections.deque` обработай задачи строго FIFO. Добавь справа и извлеки слева. Покажи ожидаемый порядок минимум для пяти id.

### E12. Ограниченная история

Используй `deque(maxlen=3)` для последних трёх просмотренных VIN. Покажи автоматическое вытеснение самого старого элемента.

### E13. Три минимальные цены

Через `heapq` найди три минимальные цены. Не считай внутренний heap полностью отсортированным. Обработай вход короче трёх элементов.

### E14. DFS дерева

Создай маленький `TreeNode` и верни значения preorder DFS. Разрешается рекурсия или явный stack. Нарисуй используемое дерево комментарием.

### E15. BFS дерева

Для того же дерева верни значения по уровням через deque. Не используй `pop(0)`.

### E16. Bubble sort

Верни новый отсортированный список, не меняя исходный. Добавь раннее завершение, если за проход не было обменов. Посчитай сравнения для уже отсортированного и обратного входа.

### E17. Selection sort

Верни новый список. На каждом шаге найди индекс минимума оставшегося диапазона. Запиши, почему уже отсортированный вход всё равно требует `O(n²)` сравнений.

### E18. Insertion sort

Верни новый список. Проверь уже отсортированный, обратный и список с дубликатами. Для записей `(price, original_position)` покажи стабильность при сортировке только по price.

### Обязательные сценарии

1. Пустая и непустая структура.
2. Попытка извлечения из пустого stack по выбранному контракту.
3. Все шесть строк со скобками.
4. FIFO-порядок не зависит от значений id.
5. `deque(maxlen)` сохраняет только последние три VIN.
6. Heap-задача для 0, 1, 2, 3 и более цен.
7. DFS и BFS одного дерева дают ожидаемо разный порядок.
8. Каждая сортировка обрабатывает пустой список, один элемент, дубликаты и отрицательные числа.
9. Исходные списки после сортировки не изменены.
10. Оценки времени и памяти записаны.

### Критерий приёмки

- E09–E18 корректны;
- структура выбрана по требуемым операциям;
- heap не назван полностью отсортированным;
- обходы дерева не теряют узлы;
- три сортировки реализованы самостоятельно;
- стабильность и in-place/out-of-place объяснены;
- счётчики сравнений подтверждают, но не заменяют асимптотический анализ.

## День 3. Рекурсия, продвинутые сортировки и medium-задачи

### Документация

### Паспорт дня

- **Цель:** строить рекурсивные решения с базовым случаем и комбинировать знакомые структуры в задачах средней сложности.

- **Готово, если:** у рекурсии есть достижимый базовый случай; вход не теряется неожиданно; все сортировки проверены на дублях и уже отсортированном списке; решения medium-задач объясняются шаг за шагом.

### E25. Radix sort

## День 4. Память CPython и профилирование

### Документация

- [Модуль `tracemalloc`](https://docs.python.org/3/library/tracemalloc.html) — отслеживание выделения памяти в Python.
- [The Python Profilers](https://docs.python.org/3/library/profile.html) — профилирование времени выполнения.

Файл: `day_04_memory_profiling.py`.

### Паспорт дня

- **Цель:** наблюдать ссылки и потребление ресурсов и оптимизировать только подтверждённое узкое место.
- **Результат:** восемь воспроизводимых экспериментов с identity, reference count, циклом ссылок, `getsizeof`, `tracemalloc`, `timeit` и `cProfile`.
- **Порядок:** проведи малые опыты со ссылками; создай и убери цикл; сравни shallow size; затем снимай память и время; найди одну горячую функцию профилировщиком и измени только её.
- **Готово, если:** наблюдение отделено от предположения; временная диагностика подписана; замеры повторяемы; оптимизированная версия сохраняет результат; выводы учитывают ограничения инструментов.
- **Пример поведения:** отчёт показывает baseline и результат после изменения вместе с одинаковым функциональным ответом.
- **Обязательно:** восемь опытов и сценарии. **Рекомендация:** не делать вывод по единственному очень короткому замеру.

Теория: главы 24–30 и прогнозы 6–7.

### 1. Ссылки и identity

Создай alias списка и отдельную поверхностную копию. Через `is`, `==` и изменения покажи разницу. Объясни, какие объекты реально создавались.

### 2. `del` и reference count

На отдельном простом объекте исследуй `sys.getrefcount()` до и после создания alias и удаления имени. Не ожидай конкретного абсолютного числа; проверяй только объяснимое изменение.

### 3. Цикл ссылок

Создай два контейнера, ссылающихся друг на друга. Удали внешние имена и выполни контролируемый `gc.collect()` для наблюдения. Не добавляй `__del__` и не используй результат как точный production-metric.

### 4. Shallow size

Сравни `sys.getsizeof()`:

- пустого и заполненного list;
- списка с короткой и очень длинной строкой;
- generator object и готового списка.

Объясни, что именно не вошло в цифру внешнего контейнера.

### 5. `tracemalloc`

Напиши helper, который измеряет current и peak Python allocations для заданной функции. Между экспериментами корректно запускай и останавливай tracing.

Сравни обработку 100_000 чисел:

- построить полный список квадратов и просуммировать;
- передать generator expression в `sum()`.

Результаты вычисления должны совпадать.

### 6. `timeit`

Сравни membership в list и set для существующего элемента в конце/отсутствующего элемента на нескольких размерах. Подготовка структур не входит в измеряемое выражение.

Запиши несколько повторов, а не один результат.

### 7. `cProfile`

Создай маленький workload из нескольких функций, где одна намеренно выполняет больше работы. Запусти профиль и выпиши:

- число вызовов;
- `tottime`;
- cumulative time;
- функцию-кандидат на оптимизацию.

Не изменяй код, пока не сохранишь baseline.

### 8. Осмысленная оптимизация

Реализуй поиск дубликатов двумя способами:

- вложенные проходы;
- set.

Проверь одинаковый контракт, оцени Big O, измерь несколько размеров и опиши цену ускорения по памяти.

### Обязательные сценарии

1. Alias и копия различаются.
2. После `del` объект остаётся доступен через второе имя.
3. Цикл создаётся и эксперимент завершается.
4. Shallow size не выдаётся за рекурсивный размер.
5. List и generator вычисляют одинаковую сумму.
6. `tracemalloc` сравнивает одинаковую работу.
7. `timeit` имеет несколько повторов и размеров.
8. Профиль запускается и интерпретируется.
9. Оптимизированная функция сохраняет результат.
10. В `notes.md` записаны ограничения каждого эксперимента.

### Критерий приёмки

- reference counting описывается как особенность CPython;
- `del` не называется прямым удалением объекта;
- циклический GC и контекстный менеджер не смешиваются;
- память и время измерены отдельными инструментами;
- benchmark и profiler решают разные вопросы;
- оптимизация имеет baseline и trade-off.

## День 5. GIL, потоки, процессы и futures

### Документация

- [Модуль `concurrent.futures`](https://docs.python.org/3/library/concurrent.futures.html) — единый интерфейс запуска задач в потоках и процессах.

Файл: `day_05_threads_processes.py`.

### Паспорт дня

- **Цель:** выбирать последовательное выполнение, threads или processes по характеру нагрузки и безопасно получать результаты Future.
- **Результат:** классификация задач, I/O и CPU baselines, два executor, завершённые Future, демонстрация race condition и исправление Lock.
- **Порядок:** классифицируй нагрузки; измерь последовательный I/O; добавь threads и обработку Future; воспроизведи гонку; защити её; затем сравни CPU-задачу последовательно и в process pool.
- **Готово, если:** все executors закрываются; исключения Future получены и видны; гонка воспроизводится и объясняется; process-код безопасен для запуска; сравнение времени не обещает гарантированное ускорение.
- **Пример поведения:** несколько искусственных I/O-задач завершаются с теми же результатами, но в другом порядке через `as_completed()`.
- **Обязательно:** девять пунктов и сценарии. **Рекомендация:** ограничить размеры CPU-нагрузки, чтобы учебный запуск оставался коротким.

Теория: главы 31–37 и прогнозы 8–9.

Все задержки делай короткими: обычно 0.02–0.1 секунды. Не выполняй реальные сетевые запросы.

### 1. Классификация задач

Для десяти примеров письменно выбери I/O-bound, CPU-bound или mixed: ожидание API, чтение файла, `sleep`, вычисление простых чисел, парсинг маленького JSON, сжатие, SQL-запрос, рендер изображения, отправка email, суммирование 100 элементов.

Для каждого предложи последовательный код, threads, processes или необходимость сначала измерить.

### 2. Последовательный I/O baseline

Создай `simulate_blocking_request(task_id, delay)`, использующую `time.sleep`, и последовательно обработай 8 задач. Верни результаты, не только напечатай их. Измерь wall-clock время.

### 3. `ThreadPoolExecutor`

Обработай тот же вход через ограниченное число workers. Сравни нормализованные результаты с baseline. Измерь несколько повторов, но не утверждай обязательное ускорение через `assert`.

### 4. `submit`, `Future`, `as_completed`

Запусти задачи с разными задержками. Сохрани:

- входной порядок;
- порядок завершения;
- итог, отсортированный по id.

Одна worker-функция намеренно вызывает `ValueError`. Coordinator обязан получить и записать ошибку, не потеряв остальные результаты.

### 5. Race condition

Создай общий склад с операцией «если stock > 0, затем уменьшить». С помощью двух потоков и небольшой контролируемой паузы между проверкой и изменением воспроизведи нарушение либо объясни, почему конкретный запуск не гарантирует его проявление.

Тест гонки не должен зависеть от того, что она обязательно проявится каждый раз.

### 6. `Lock`

Защити составную операцию одним `threading.Lock`. Проверь многократными запусками:

- stock не становится отрицательным;
- число успешных продаж не превышает исходный stock;
- lock не удерживается во время лишнего print/sleep.

### 7. CPU baseline

Создай top-level `count_primes(limit)` или другую чистую CPU-heavy функцию с умеренным входом. Сначала проверь корректность на малых значениях и измерь последовательную обработку нескольких входов.

### 8. `ProcessPoolExecutor`

Выполни тот же CPU batch процессами. Обязательно:

- worker на верхнем уровне;
- только picklable аргументы/результаты;
- executor создаётся внутри функции;
- запуск находится под `if __name__ == "__main__"`;
- результаты совпадают с baseline;
- отсутствие ускорения на конкретной машине допускается и объясняется overhead/числом ядер/размером входа.

### 9. Thread Future и Process Future

Сравни общий API `submit`, `map`, `result`, `as_completed`, обработку исключения. Объясни, что одинаковый интерфейс не означает общую память и одинаковую стоимость.

### Обязательные сценарии

1. Пустой batch.
2. Одна и восемь I/O-задач.
3. Разные задержки и детерминированный итог.
4. Worker exception видима coordinator.
5. Executor завершается через context manager.
6. Потоковая продажа не нарушает stock после Lock.
7. CPU-функция проверена на известных малых ответах.
8. Sequential и process результаты одинаковы.
9. Импорт файла не создаёт threads/processes.
10. Полный файл завершается без зависших worker.

### Критерий приёмки

- GIL не используется как объяснение потокобезопасности;
- Future results и exceptions прочитаны;
- порядок завершения не считается стабильным;
- общая операция защищена, а критическая секция мала;
- процессы используются для отдельной CPU-задачи;
- process-код переносим для spawn;
- сравнение производительности не является тестом корректности.

## День 6. `asyncio`, coroutine, Task, Future и event loop

### Документация

- [Модуль `asyncio`](https://docs.python.org/3/library/asyncio.html) — асинхронное выполнение, задачи и цикл событий.

Файл: `day_06_asyncio.py`.

### Паспорт дня

- **Цель:** запускать конкурентные I/O-операции в одном event loop и не блокировать его синхронной работой.
- **Результат:** девять опытов с coroutine object, последовательным await, Task, gather, ошибкой незапущенной coroutine, блокировкой, `to_thread` и Queue.
- **Порядок:** создай coroutine и исследуй момент выполнения; сравни последовательный и конкурентный запуск; обработай результаты/ошибки `gather`; покажи блокировку; вынеси её; затем собери producer-consumer.
- **Готово, если:** нет забытых await; все созданные Task завершены или отменены осознанно; блокирующая функция не остаётся в event loop; Queue корректно завершает обработку; времена объяснимы.
- **Пример поведения:** три ожидания по одной секунде через задачи завершаются примерно за одну, а не за три секунды, без утверждения о точном времени.
- **Обязательно:** девять пунктов и сценарии. **Рекомендация:** подписывать временными логами момент старта и завершения каждой coroutine.

Теория: главы 38–45 и прогнозы 10–12.

### 1. Coroutine function и object

Создай `async def fetch_car(task_id, delay)`. Отдельно получи coroutine object без немедленного выполнения тела, исследуй его тип, затем корректно await его внутри `main`.

Не оставляй ни одной coroutine never awaited.

### 2. Последовательный await

Выполни три `fetch_car` последовательными await и измерь время. Сохрани результаты.

### 3. `create_task`

Создай три Task до первого ожидания результата. Дай задачам имена через параметр `name` и await каждую. Сравни результат и время с последовательным вариантом.

### 4. `gather`

Передай операции с разными задержками. Докажи отдельно:

- порядок завершения может отличаться;
- список `gather` соответствует порядку аргументов.

Не полагайся на точные миллисекунды.

### 5. Ошибка coroutine

Одна задача вызывает `ValueError`. Покажи обычное распространение исключения из await. Затем создай отдельную безопасную wrapper-coroutine, превращающую только ожидаемую ошибку в явный `TaskResult`.

Не применяй бездумно `return_exceptions=True`.

### 6. Блокировка event loop

Сравни временную демонстрацию с `time.sleep` внутри coroutine и с `await asyncio.sleep`. В финальной рабочей реализации `time.sleep` внутри coroutine быть не должно.

Объясни, почему наличие `async def` само по себе не спасает loop.

### 7. `asyncio.to_thread`

Вызови уже существующую блокирующую I/O-имитацию через `await asyncio.to_thread(...)`. Покажи, что event loop может в это время выполнять heartbeat-coroutine.

Не используй `to_thread` как решение pure-Python CPU benchmark.

### 8. `asyncio.Queue`

Создай очередь из нескольких task id и 2–3 worker-coroutines. Каждый `get()` должен иметь `task_done()` в `finally`. Дождись `queue.join()`, затем корректно останови workers через sentinel.

Результат нормализуй по id. Не реализуй пока приоритеты, rate limiting и сложную отмену.

### 9. Task и Future

Через `isinstance(task, asyncio.Future)` покажи связь типов и письменно объясни:

- coroutine object описывает приостанавливаемое вычисление;
- Task планирует coroutine;
- Future представляет будущий результат;
- вручную создавать Future в этом задании не нужно.

### Обязательные сценарии

1. Пустой список операций.
2. Одна и несколько coroutine.
3. Последовательный и concurrent результаты одинаковы.
4. Разные задержки не ломают порядок нормализованного отчёта.
5. Ожидаемая ошибка отражена в результате.
6. Неожиданная ошибка не скрывается.
7. В рабочем async-пути нет `time.sleep`.
8. Heartbeat выполняется во время `to_thread`.
9. Queue завершается и все задачи отмечены.
10. После `asyncio.run(main())` не остаётся незавершённых задач.

### Критерий приёмки

- нет RuntimeWarning о never-awaited coroutine;
- concurrency создаётся планированием до ожидания результатов;
- event loop объясняется как cooperative scheduler;
- Task и Future не смешиваются с thread Future;
- blocking I/O вынесен осознанно;
- ошибки и результаты наблюдаемы;
- порядок завершения не используется как бизнес-порядок.

## День 7. Итоговый проект «Task Dispatcher»

### Документация

- [Модуль `concurrent.futures`](https://docs.python.org/3/library/concurrent.futures.html) — исполнители задач и объекты `Future` для итогового диспетчера.

### Паспорт дня

- **Цель:** реализовать один набор задач через несколько стратегий исполнения и доказать корректность выбора для I/O и CPU нагрузки.
- **Результат:** пакет указанной структуры, четыре runner-а, единый формат результатов, benchmarks и CLI-демонстрация.
- **Порядок:** определи модель задачи/результата; реализуй workloads; сделай последовательный baseline; затем threaded, async и process runners; после корректности добавь benchmark и сводный вывод.
- **Готово, если:** одинаковый набор задач даёт эквивалентные результаты; ошибки одной задачи не теряются; ресурсы закрываются; async не блокируется; process runner запускается корректно; сравнение содержит условия эксперимента.
- **Пример поведения:** итоговая таблица показывает стратегию, тип нагрузки, число задач, время и число успехов/ошибок.
- **Обязательно:** вся структура, сценарии и архитектурные ограничения. **Рекомендация:** реализовать сначала один сквозной I/O-сценарий во всех runner-ах, затем добавлять остальные.

Теория: главы 31–47 и повтор глав измерения.

### Назначение

Создать лабораторию обработки фоновых задач автосалона. Один и тот же набор I/O-подобных задач выполняется тремя способами:

1. последовательно;
2. несколькими потоками;
3. несколькими coroutine через `asyncio`.

Отдельный CPU batch сравнивает последовательное выполнение и процессы. Проект не обращается к сети и не требует внешних библиотек.

### Структура

```text
day_07_task_dispatcher/
├── __init__.py
├── models.py
├── workloads.py
├── sequential_runner.py
├── threaded_runner.py
├── async_runner.py
├── process_runner.py
├── benchmarks.py
└── main.py
```

### `models.py`

Определи:

- `TaskKind` Enum минимум с `EMAIL`, `REPORT`, `SYNC`;
- frozen dataclass `TaskSpec`: уникальный положительный id, kind, неотрицательная короткая задержка, строковый payload и флаг учебной ожидаемой ошибки;
- frozen dataclass `TaskResult`: task id, success, value либо error и необязательное имя worker;
- инвариант: успешный результат не содержит error, ошибочный содержит непустую error.

Не помещай реальные email, токены и персональные данные в payload или логи.

### `workloads.py`

Реализуй:

- `run_blocking_io_task(task) -> TaskResult` через короткий `time.sleep`;
- `async run_async_io_task(task) -> TaskResult` через `await asyncio.sleep`;
- top-level `count_primes(limit: int) -> int` для CPU-демонстрации.

Blocking и async версии должны применять одинаковые правила результата. Не вызывай одну из них из другой ценой блокировки event loop.

### `sequential_runner.py`

`run_sequential(tasks) -> list[TaskResult]` перекладывает задачи в `collections.deque` и обрабатывает их по одной в порядке FIFO. Пустой вход возвращает пустой список. Ожидаемая ошибка одной задачи представлена явным результатом и не останавливает весь batch.

### `threaded_runner.py`

Реализуй producer/consumer через:

- `queue.Queue`;
- заданное положительное число worker threads;
- sentinel для остановки;
- `task_done()` в `finally`;
- `queue.join()`;
- безопасный сбор результатов;
- обязательное завершение всех threads.

Не удерживай lock во время имитации I/O. Итог сортируется по task id.

### `async_runner.py`

Реализуй:

- `asyncio.Queue`;
- заданное положительное число coroutine workers;
- `await queue.join()`;
- sentinel и корректное завершение worker tasks;
- async workload без `time.sleep`;
- итог, отсортированный по task id.

`asyncio.run()` находится только в `main.py`, не внутри runner.

### `process_runner.py`

Реализуй `run_cpu_batch(limits) -> list[int]` через `ProcessPoolExecutor`. Worker импортируется с верхнего уровня. Результаты сохраняют порядок входов или явно нормализуются.

Не передавай в процесс lock, открытую очередь, coroutine или непиклируемую closure.

### `benchmarks.py`

Создай функции измерения, которые:

- принимают callable/async callable и вход;
- выполняют несколько повторов;
- возвращают сырые времена и понятное summary;
- не смешивают подготовку разных входов с выполнением;
- не утверждают корректность по времени;
- не требуют обязательного ускорения.

Для async measurement не вызывай вложенный `asyncio.run()` внутри уже работающего loop.

### `main.py`

Точка сборки:

- создаёт не меньше 8 детерминированных `TaskSpec` с разными короткими задержками;
- включает минимум одну ожидаемо ошибочную задачу;
- запускает три I/O-режима на одном логическом входе;
- проверяет равенство нормализованных результатов без поля worker;
- печатает краткую таблицу времени;
- запускает небольшой sequential/process CPU batch;
- печатает вывод о выборе модели без обещания ускорения;
- защищена `if __name__ == "__main__"`.

### Обязательные сценарии

1. Пустой batch во всех трёх I/O-режимах.
2. Одна корректная задача.
3. Восемь корректных задач с разными задержками.
4. Одна ожидаемая ошибка среди успешных задач.
5. Повторяющийся task id отвергается до запуска workers.
6. Нулевая задержка разрешена.
7. Отрицательная задержка запрещена.
8. `worker_count = 1`.
9. Несколько workers.
10. `worker_count <= 0` отвергается.
11. Sequential, threaded и async дают одинаковый бизнес-результат.
12. Итог детерминированно отсортирован по id.
13. Thread queue не зависает и каждый thread завершён.
14. Async queue не оставляет pending tasks.
15. Ожидаемая ошибка не теряется.
16. Неожиданная программная ошибка не превращается молча в success.
17. CPU-функция корректна на малых известных входах.
18. Sequential и process CPU results одинаковы.
19. Отсутствие ускорения не ломает проверки.
20. Импорт каждого модуля ничего не запускает и не печатает.

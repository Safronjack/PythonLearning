# Теория недели 4: алгоритмы, память и конкурентность

Модуль рассчитан на первое системное изучение алгоритмов и моделей конкурентного выполнения. Главная цель — научиться рассуждать: сначала доказать корректность, затем оценить сложность, после этого измерить и только потом оптимизировать.

Примеры ориентированы на CPython 3.11.9 — версию текущего учебного окружения.

## 1. Алгоритм и контракт

Алгоритм — конечная последовательность однозначных шагов, преобразующая входные данные в результат.

Для функции недостаточно сказать «она ищет автомобиль». Нужен контракт:

- какие входы допустимы;
- какой результат возвращается;
- что происходит, если значения нет;
- изменяется ли вход;
- какие ошибки возможны;
- требуется ли предварительная сортировка;
- какова стоимость по времени и памяти.

```python
def find_index_by_vin(vins: list[str], target: str) -> int | None:
    """Вернуть индекс первого target или None, не изменяя vins."""
    for index, vin in enumerate(vins):
        if vin == target:
            return index
    return None
```

До анализа скорости сначала проверь:

- пустой список;
- один элемент;
- элемент в начале, середине и конце;
- отсутствующий элемент;
- повторяющееся значение и обещание «первый индекс».

Быстрый неверный алгоритм остаётся неверным.

## 2. Что измеряет Big O

Big O описывает, как верхняя граница количества операций растёт при увеличении размера входа `n`. Она не показывает точное время в секундах.

Частые классы роста:

| Обозначение | Название | Пример |
|---|---|---|
| `O(1)` | константное | чтение `items[index]` |
| `O(log n)` | логарифмическое | бинарный поиск |
| `O(n)` | линейное | один полный проход |
| `O(n log n)` | линейно-логарифмическое | эффективная comparison sort |
| `O(n²)` | квадратичное | вложенное сравнение всех пар |
| `O(2ⁿ)` | экспоненциальное | полный перебор многих подмножеств |
| `O(n!)` | факториальное | перебор всех перестановок |

При асимптотической оценке постоянные множители и слагаемые меньшего порядка отбрасывают:

```text
3n + 20       → O(n)
n² + 100n     → O(n²)
5             → O(1)
```

Это не означает, что константы не важны в реальной производительности. Big O отвечает на вопрос роста, измерение — на вопрос фактической стоимости в конкретной среде.

## 3. Как считать циклы

Один цикл по `n` элементам обычно даёт `O(n)`:

```python
for car in cars:
    inspect(car)
```

Два последовательных цикла дают `O(n + n) = O(n)`, а не `O(n²)`:

```python
for car in cars:
    validate(car)

for car in cars:
    report(car)
```

Вложенный полный цикл обычно даёт `O(n²)`:

```python
for first in cars:
    for second in cars:
        compare(first, second)
```

Если размеры независимы, сохраняй разные обозначения: обход `n` автомобилей и `m` покупателей во вложенных циклах — `O(n * m)`.

Не оценивай сложность только по количеству строк. Вызов функции внутри цикла может сам содержать обход.

## 4. Лучший, средний, худший и амортизированный случаи

Линейный поиск:

- лучший случай: элемент первый — `O(1)`;
- худший: элемент последний или отсутствует — `O(n)`;
- средний при разумной модели распределения — `O(n)`.

Амортизированная оценка распределяет редкую дорогую операцию по длинной серии. `list.append()` обычно `O(1)` амортизированно: иногда внутренний массив расширяется и элементы копируются, но это происходит не при каждом добавлении.

Всегда уточняй, какой случай называешь. Фраза «быстро» без входа и границы мало полезна.

## 5. Дополнительная память

Space complexity показывает рост дополнительной памяти относительно размера входа.

```python
def doubled(values: list[int]) -> list[int]:
    return [value * 2 for value in values]
```

Новый список хранит `n` ссылок: дополнительная память `O(n)`.

```python
def iter_doubled(values: list[int]):
    for value in values:
        yield value * 2
```

Сам генератор хранит небольшое состояние текущего шага: дополнительная память обработки обычно `O(1)`, если потребитель тоже не собирает все результаты в список.

Нужно заранее договориться, учитываем ли вход и выход. Обычно при анализе алгоритма отдельно называют auxiliary space — дополнительную память помимо входа и обязательного результата.

Рекурсивные вызовы тоже занимают стек. Рекурсивный обход глубины `h` использует минимум `O(h)` памяти стека.

## 6. Стоимость стандартных коллекций

Для обычного CPython полезны ориентиры:

| Операция | Ожидаемая стоимость |
|---|---:|
| `list[index]` | `O(1)` |
| `list.append(value)` | амортизированно `O(1)` |
| `list.pop()` с конца | `O(1)` |
| `list.insert(0, value)` / `pop(0)` | `O(n)` |
| `value in list` | `O(n)` |
| `key in dict` / `value in set` | в среднем `O(1)`, теоретически хуже |
| вставка в `dict`/`set` | в среднем амортизированно `O(1)` |
| `sorted(values)` | `O(n log n)` в худшем случае |
| `deque.append/popleft` | `O(1)` с нужного конца |
| `heapq.heappush/heappop` | `O(log n)` |
| чтение минимума `heap[0]` | `O(1)` |

Оценка dict/set зависит от корректного хеширования. Коллизии разрешаются внутри хеш-таблицы; «в среднем O(1)» не является математической гарантией для любого специально построенного ввода.

## 7. Измерение не заменяет анализ

Можно измерить два списка длиной 100 и случайно получить почти одинаковое время для `O(n)` и `O(n²)`. Причины:

- вход слишком маленький;
- шум операционной системы;
- прогрев кэшей;
- различная стоимость самих операций;
- один неудачный замер;
- данные представляют только лучший случай.

Правильный порядок:

1. определить контракт и доказать корректность на сценариях;
2. вывести асимптотику из структуры алгоритма;
3. измерить несколько размеров и повторов;
4. проверить гипотезу;
5. профилировать реальную программу перед оптимизацией.

## 8. Линейный поиск

```python
def linear_search(values: list[int], target: int) -> int | None:
    for index, value in enumerate(values):
        if value == target:
            return index
    return None
```

Сортировка не требуется. Лучший случай `O(1)`, худший `O(n)`, дополнительная память `O(1)`.

Если нужны все индексы, ранний `return` больше не подходит и выход может занимать `O(k)`, где `k` — число совпадений.

## 9. Бинарный поиск

Бинарный поиск на каждом шаге отбрасывает половину диапазона, поэтому работает за `O(log n)`. Обязательное предусловие: данные отсортированы по тому же ключу, который сравнивается.

```python
def binary_search(values: list[int], target: int) -> int | None:
    left = 0
    right = len(values) - 1

    while left <= right:
        middle = (left + right) // 2
        value = values[middle]

        if value == target:
            return middle
        if value < target:
            left = middle + 1
        else:
            right = middle - 1

    return None
```

Инвариант цикла: если target ещё может находиться в списке, он находится в закрытом диапазоне `[left, right]`.

Типичные ошибки:

- `right = len(values)` при схеме с закрытыми границами;
- цикл `left < right`, который не проверяет последний кандидат;
- присваивание `left = middle`, из-за которого диапазон иногда не уменьшается;
- применение к несортированным данным;
- сортировка перед каждым единичным поиском: она стоит `O(n log n)` и может сделать линейный поиск дешевле для одного запроса.

В стандартной библиотеке для поиска позиции вставки существует `bisect`. Он находит позицию за `O(log n)`, но вставка в середину list остаётся `O(n)` из-за сдвига элементов.

## 10. Стек

Стек работает по принципу LIFO: last in, first out.

Подходящие операции list:

```python
stack: list[str] = []
stack.append("validate")
stack.append("charge")
last_operation = stack.pop()
```

Добавление и удаление с конца — `O(1)` амортизированно/`O(1)`. Стек применяют для:

- истории отмены;
- обхода в глубину;
- проверки скобок;
- моделирования вызовов.

Обращение к пустому стеку нужно определить контрактом: `None`, собственная ошибка или стандартный `IndexError`.

## 11. Очередь и `deque`

Очередь FIFO: first in, first out.

Удаление `list.pop(0)` стоит `O(n)`. Для двусторонней очереди есть `collections.deque`:

```python
from collections import deque

tasks = deque(["validate", "charge"])
tasks.append("notify")
next_task = tasks.popleft()
```

Операции на обоих концах deque — `O(1)`. Произвольный доступ в середине не является его сильной стороной.

`queue.Queue` появится в потоковой практике: она добавляет безопасную координацию производителей и потребителей между потоками.

## 12. Heap / приоритетная очередь

Heap хранит частичный порядок. В min-heap минимальный элемент находится в позиции 0, но весь список не отсортирован.

```python
import heapq

prices = [50_000, 31_000, 42_000]
heapq.heapify(prices)
cheapest = heapq.heappop(prices)
```

- `heapify` — `O(n)`;
- чтение минимума — `O(1)`;
- push/pop — `O(log n)`.

Heap полезен, когда постоянно нужен следующий элемент с наивысшим приоритетом или несколько лучших элементов. Для полного однократного упорядочивания обычно проще `sorted()`.

Если приоритеты равны и payload нельзя сравнивать, храни tuple `(priority, sequence_number, payload)`, чтобы sequence number стабильно разрешал равенство.

## 13. Дерево и обходы

Узел бинарного дерева хранит значение и ссылки на левое и правое поддеревья. Дерево не обязано быть бинарным деревом поиска.

В binary search tree соблюдается правило порядка. Если дерево сбалансировано, поиск близок к `O(log n)`. Если элементы добавлены неудачно и дерево превратилось в цепочку, поиск становится `O(n)`.

DFS идёт в глубину и использует стек или рекурсию. BFS идёт по уровням и использует очередь.

Для дерева из `n` узлов полный обход — `O(n)`. Память зависит от формы:

- рекурсивный DFS — `O(h)` стек, где `h` — высота;
- BFS — `O(w)`, где `w` — максимальная ширина.

На этой неделе достаточно построить маленькое дерево и реализовать обходы. Балансировку писать не нужно.

## 14. Свойства сортировки

Перед сравнением алгоритмов различай:

- comparison sort — порядок строится сравнением элементов;
- stable — равные ключи сохраняют исходный относительный порядок;
- in-place — используется небольшая дополнительная память вместо нового массива размера `n`;
- adaptive — алгоритм использует уже существующий порядок данных;
- worst/average/best case.

Контракт функции обязан сказать, меняет ли она вход. Для учебных реализаций удобно принимать список и возвращать новый, если задание не требует in-place.

## 15. Bubble sort

Соседние элементы сравниваются и меняются местами, пока большие «всплывают» к концу.

- худший и средний случаи: `O(n²)`;
- лучший с флагом отсутствия обменов: `O(n)`;
- дополнительная память: `O(1)` для in-place;
- стабильность сохраняется, если равные элементы не менять местами.

Практическая ценность — увидеть инвариант прохода и квадратичный рост. Для production используй встроенную сортировку.

## 16. Selection sort

На каждой позиции ищется минимум оставшейся части.

- лучший, средний, худший: `O(n²)` сравнений;
- дополнительная память `O(1)` для in-place;
- типичная реализация нестабильна;
- число обменов невелико, но сравнений всё равно квадратично.

Уже отсортированный вход не делает обычный selection sort линейным.

## 17. Insertion sort

Очередной элемент вставляется в правильное место уже обработанной части.

- лучший случай для отсортированных данных: `O(n)`;
- средний и худший: `O(n²)`;
- обычно stable и in-place;
- полезен на маленьких или почти отсортированных данных.

Именно такие свойства важнее запоминания строк реализации.

## 18. Merge sort

Алгоритм делит данные пополам, сортирует части и сливает их.

- время: `O(n log n)` во всех основных случаях;
- дополнительная память обычной реализации: `O(n)`;
- легко сделать стабильным;
- рекурсивная версия дополнительно использует стек `O(log n)` при сбалансированном делении.

Главная операция — линейное слияние двух отсортированных последовательностей. Если использовать `pop(0)` на list, можно случайно ухудшить стоимость; лучше двигать два индекса.

## 19. Quicksort

Выбирается pivot, элементы разделяются относительно него, части сортируются.

- средний случай: `O(n log n)`;
- худший: `O(n²)` при неудачных разбиениях;
- типичная учебная реализация нестабильна;
- память зависит от реализации и глубины рекурсии.

Версия с тремя новыми списками проста, но не in-place и использует дополнительную память. Версия с индексами сложнее и легче содержит ошибку. В учебной неделе сначала важны контракт и корректное разбиение.

Выбор первого элемента pivot на уже отсортированном входе часто создаёт худший случай.

## 20. Heap sort

Heap sort строит heap и последовательно извлекает элементы либо перестраивает границу heap внутри массива.

- время худшего случая: `O(n log n)`;
- классический вариант in-place;
- нестабилен;
- хороший выбор, когда важна гарантированная асимптотика и ограниченная дополнительная память, но в обычном Python встроенная сортировка практичнее.

Учебную реализацию можно построить через `heapq` с новым результатом; тогда дополнительная память будет `O(n)` и это нужно честно записать.

## 21. Radix sort

Radix sort не сравнивает каждую пару элементов. Он обрабатывает разряды ключа.

Для неотрицательных целых и основания `k` со `d` разрядами типичная оценка:

```text
O(d * (n + k))
```

Нужны ограничения на тип ключа, стабильная сортировка по каждому разряду и дополнительная память. Отрицательные числа и произвольные объекты требуют отдельной стратегии. Нельзя просто объявить radix sort универсально `O(n)` без `d` и `k`.

## 22. Встроенная сортировка Python

`list.sort()` меняет список и возвращает `None`. `sorted(iterable)` создаёт новый список.

```python
cars = [
    {"model": "Camry", "price": 31_000},
    {"model": "A6", "price": 42_000},
]

ordered = sorted(cars, key=lambda car: (car["price"], car["model"]))
```

Python использует стабильный Timsort. Стабильность позволяет выполнять несколько сортировок по ключам и сохранять относительный порядок равных элементов. Timsort адаптивен и использует существующие упорядоченные участки.

В production не переписывай сортировку вручную без измеримой причины. Учебные реализации нужны для понимания компромиссов.

## 23. Рекурсия

Рекурсивная функция вызывает себя для меньшей подзадачи.

```python
def factorial(number: int) -> int:
    if number < 0:
        raise ValueError("number must be non-negative")
    if number <= 1:
        return 1
    return number * factorial(number - 1)
```

Нужны:

- достижимый базовый случай;
- шаг, приближающий вход к базе;
- контракт для недопустимых значений;
- понимание глубины стека.

CPython не выполняет tail-call optimization. Очень глубокая рекурсия заканчивается `RecursionError`; увеличивать recursion limit без анализа опасно. Для длинной линейной последовательности цикл обычно надёжнее.

Рекурсия естественна для деревьев и divide-and-conquer, но не обязана быть лучшим решением каждой задачи.

## 24. Имя, ссылка и объект в памяти

Присваивание связывает имя с объектом:

```python
first = ["VIN-1"]
second = first
second.append("VIN-2")
print(first)
```

Новый список не создавался. Оба имени ссылаются на один объект. Это уже наблюдалось при изучении изменяемости; теперь важно связать поведение с памятью.

Контейнер обычно хранит ссылки на элементы, а не встраивает полные Python-объекты в себя.

## 25. Reference counting в CPython

CPython в основном освобождает объект, когда число сильных ссылок на него становится нулём.

```python
import sys

cars = []
alias = cars
print(sys.getrefcount(cars))
```

`sys.getrefcount()` сам временно получает ссылку, поэтому результат на единицу выше наблюдаемого числа ссылок. Точное значение зависит от контекста и является диагностикой реализации CPython, а не бизнес-контрактом.

`del alias` удаляет имя, а не обязательно объект. Если остаётся `cars`, объект жив.

Другие реализации Python могут управлять памятью иначе. Не строй прикладную логику на моменте уничтожения объекта.

## 26. Циклический сборщик мусора

Reference counting не может самостоятельно удалить цикл:

```python
first: list[object] = []
second: list[object] = [first]
first.append(second)
```

После удаления внешних имён объекты всё ещё ссылаются друг на друга. Циклический garbage collector CPython ищет недостижимые циклы среди отслеживаемых контейнерных объектов.

Модуль `gc` позволяет наблюдать и запускать сборку в эксперименте. Не вызывай `gc.collect()` после каждой операции в обычном приложении: это не стандартная оптимизация.

Для файлов, соединений и блокировок используй контекстные менеджеры. Нельзя полагаться на то, что финализация объекта мгновенно освободит внешний ресурс.

## 27. `sys.getsizeof()` и shallow size

```python
import sys

values = ["Camry", "A6", "X5"]
print(sys.getsizeof(values))
```

`getsizeof` показывает размер самого контейнера и внутреннюю служебную часть, но не рекурсивную сумму всех объектов, на которые он ссылается. Сравнение списка из коротких и длинных строк только по размеру внешнего списка вводит в заблуждение.

Объекты могут разделяться между контейнерами, поэтому «сложить размеры всего рекурсивно» тоже требует защиты от повторного подсчёта и циклов.

## 28. `tracemalloc`

`tracemalloc` отслеживает выделения памяти Python и позволяет сравнивать снимки или текущий/пиковый объём.

```python
import tracemalloc

tracemalloc.start()
values = [number * 2 for number in range(100_000)]
current, peak = tracemalloc.get_traced_memory()
tracemalloc.stop()

print(current, peak)
```

Измеряй одинаковый участок, очищай состояние между экспериментами и записывай размер входа. Инструмент сам добавляет overhead, а цифры не равны всей памяти процесса.

Для сравнения list comprehension и generator нужно потреблять одинаковый объём полезной работы. Если генератор вообще не обойти, сравнение нечестно.

## 29. Benchmarking: `perf_counter` и `timeit`

`time.perf_counter()` подходит для измерения участка программы по wall-clock времени:

```python
from time import perf_counter

started = perf_counter()
result = sum(range(100_000))
elapsed = perf_counter() - started
```

Для маленьких фрагментов `timeit` автоматически выполняет повторы. Один запуск не является надёжным benchmark.

Правила:

- проверяй одинаковый результат;
- используй несколько повторов;
- не включай лишний print;
- прогревай или учитывай первый запуск;
- сравнивай несколько размеров;
- не делай жёсткий `assert`, что конкурентная версия обязана быть быстрее;
- описывай машину и среду, если цифры публикуются.

## 30. Profiling: `cProfile`

Benchmark отвечает «сколько заняло?». Profiler помогает найти «где потрачено время?».

```text
python3 -m cProfile -s cumulative program.py
```

`cProfile` показывает число вызовов и время функций. Профилировщик добавляет overhead, поэтому его отчёт используют для поиска кандидатов, а не как абсолютный benchmark.

Сначала найди горячий участок, затем оптимизируй и снова проверь корректность и измерения. Не ускоряй код, который не влияет на реальную нагрузку.

## 31. Concurrency и parallelism

Concurrency — несколько задач находятся в прогрессе за один период и чередуются. Parallelism — несколько вычислений физически выполняются одновременно.

Один event loop обычно даёт concurrency без параллельного исполнения Python-кода. Несколько процессов могут дать настоящий CPU parallelism на нескольких ядрах.

Асинхронность — способ организации ожидания и продолжений. Она не является синонимом потоков и не гарантирует ускорение любой задачи.

## 32. I/O-bound и CPU-bound

I/O-bound задача большую часть времени ждёт:

- сеть;
- диск;
- базу данных;
- внешний API;
- таймер.

CPU-bound задача большую часть времени вычисляет:

- обработка большого числа элементов;
- сжатие или кодирование;
- сложная математика;
- вычисление хешей;
- обработка изображений.

Имитация ожидания через `sleep` помогает увидеть планирование, но не доказывает производительность реальной сети.

Ориентир для CPython 3.11:

| Задача | Обычно рассмотреть |
|---|---|
| Несколько простых операций | последовательный код |
| Блокирующий I/O | потоки |
| Очень много async-совместимых I/O операций | `asyncio` |
| Чистый Python CPU-bound | процессы |
| CPU-heavy C extension, освобождающая GIL | измерить; потоки могут помочь |

Выбор подтверждается нагрузкой, ограничениями библиотек и измерениями.

## 33. GIL без мифов

В обычной сборке CPython 3.11 Global Interpreter Lock позволяет только одному потоку одновременно исполнять Python bytecode в одном процессе.

Из этого не следует:

- что потоков нет;
- что потоки бесполезны для I/O;
- что все составные операции автоматически потокобезопасны;
- что race condition невозможна;
- что multiprocessing тоже ограничен одним GIL;
- что любой код C-extension всегда держит GIL.

Во время блокирующего I/O поток может освободить GIL, и другой поток продолжит работу. Некоторые расширения освобождают GIL во время тяжёлых вычислений.

Не полагайся на случайную атомарность отдельной операции встроенного типа. Бизнес-инвариант часто состоит из нескольких шагов «проверить → изменить», между которыми другой поток может вмешаться.

## 34. Потоки

`threading.Thread` даёт низкоуровневое управление. Для независимых функций удобен `ThreadPoolExecutor`:

```python
from concurrent.futures import ThreadPoolExecutor
from time import sleep


def simulate_request(task_id: int) -> int:
    sleep(0.05)
    return task_id


with ThreadPoolExecutor(max_workers=4) as executor:
    results = list(executor.map(simulate_request, range(8)))
```

Контекстный менеджер корректно завершает executor. `map` возвращает результаты в порядке входов. При `submit` и `as_completed` результаты наблюдаются в порядке завершения.

### Future из `concurrent.futures`

```python
with ThreadPoolExecutor(max_workers=2) as executor:
    future = executor.submit(simulate_request, 1)
    result = future.result()
```

Future представляет будущий результат. `future.result()` возвращает его или повторно поднимает исключение worker. Если не читать результаты, можно потерять информацию об ошибке.

## 35. Race condition и Lock

Race condition возникает, когда результат зависит от непредсказуемого взаимного порядка операций.

```text
1. Поток A проверяет, что VIN отсутствует.
2. Поток B проверяет то же.
3. Оба добавляют VIN.
```

Отдельные проверки прошли, но общий инвариант уникальности нарушен. Критическую секцию «проверить и добавить» нужно защищать одним lock либо убрать общее изменяемое состояние.

```python
from threading import Lock

lock = Lock()

with lock:
    # минимальная операция над общим состоянием
    pass
```

Lock не делает весь объект автоматически безопасным. Защищай одно и то же состояние одним понятным правилом. Не удерживай lock во время долгого I/O без необходимости.

Deadlock возникает, когда участники навсегда ждут ресурсы друг друга. На этой неделе достаточно избегать нескольких lock и держать критические секции маленькими; глубокая диагностика будет позже.

## 36. `queue.Queue` для потоков

`queue.Queue` координирует producer/consumer между потоками.

Основные операции:

- `put(item)` — добавить;
- `get()` — взять, при необходимости ждать;
- `task_done()` — отметить завершение полученной задачи;
- `join()` — дождаться, когда все добавленные задачи отмечены;
- sentinel — специальное значение для остановки worker.

Для каждого успешного `get()` должен быть ровно один `task_done()`, обычно в `finally`. Иначе `join()` может ждать бесконечно.

Результаты нескольких worker могут приходить в разном порядке. Если нужен детерминированный отчёт, сортируй его по `task_id` после выполнения.

## 37. Процессы

Процессы имеют отдельную память и отдельный интерпретатор. Для pure-Python CPU-bound работы они могут использовать несколько ядер, но имеют стоимость:

- запуск процессов;
- сериализация аргументов и результатов;
- передача данных;
- дополнительная память;
- более сложная диагностика.

```python
from concurrent.futures import ProcessPoolExecutor


def count_divisors(number: int) -> int:
    return sum(1 for candidate in range(1, number + 1) if number % candidate == 0)


def main() -> None:
    with ProcessPoolExecutor() as executor:
        results = list(executor.map(count_divisors, [10_000, 10_001]))
    print(results)


if __name__ == "__main__":
    main()
```

Worker-функция должна быть импортируемой и сериализуемой — объявляй её на верхнем уровне модуля, не как lambda или локальную closure. Аргументы и результаты также должны быть picklable.

На macOS и при spawn дочерний процесс импортирует модуль. Без защиты точки входа он может повторно создавать процессы.

Общее глобальное изменение в одном процессе не становится автоматически видимым другому. Для этой недели процессы получают независимые задачи и возвращают результаты; shared memory и IPC отложены.

## 38. Coroutine function и coroutine object

```python
import asyncio


async def fetch_model(task_id: int) -> str:
    await asyncio.sleep(0.05)
    return f"model-{task_id}"


async def main() -> None:
    result = await fetch_model(1)
    print(result)


asyncio.run(main())
```

- `async def fetch_model` создаёт coroutine function;
- вызов `fetch_model(1)` создаёт coroutine object;
- тело не обязано выполняться немедленно;
- `await` приостанавливает текущую coroutine до результата awaitable;
- `asyncio.run()` создаёт event loop, выполняет top-level coroutine и закрывает loop.

Coroutine object нельзя забывать: его нужно await или запланировать как Task. Иначе возникает предупреждение `coroutine was never awaited`, а работа не выполняется.

## 39. Event loop и cooperative scheduling

Event loop выполняет готовые задачи и следит за событиями I/O и таймерами. В одном потоке он выполняет одну Task до точки, где та добровольно отдаёт управление через `await` незавершённой операции.

Это cooperative scheduling. Если coroutine делает длинный обычный цикл без await, остальные задачи ждут.

```python
async def bad_wait() -> None:
    from time import sleep
    sleep(1)  # блокирует весь поток event loop


async def good_wait() -> None:
    import asyncio
    await asyncio.sleep(1)
```

`await` сам по себе не делает синхронную CPU-функцию неблокирующей. Awaitable должна действительно отдавать управление.

## 40. Task

Task оборачивает coroutine object, планирует её выполнение в event loop и хранит состояние/результат.

```python
async def main() -> None:
    first = asyncio.create_task(fetch_model(1))
    second = asyncio.create_task(fetch_model(2))

    first_result = await first
    second_result = await second
    print(first_result, second_result)
```

Если просто дважды написать последовательный `await fetch_model(...)`, первая операция завершится до старта второй. Task позволяет им находиться в прогрессе одновременно.

Сохраняй ссылки на созданные задачи и наблюдай их результаты. Бесконтрольный fire-and-forget может потерять ошибки и завершиться при закрытии loop.

## 41. Future в `asyncio`

`asyncio.Future` — низкоуровневый awaitable, представляющий результат, который появится позже. Task является специализированным Future, выполняющим coroutine.

Прикладной код обычно:

- пишет coroutine;
- создаёт Task высокоуровневым API;
- await-ит Task или группу awaitable;
- не создаёт Future вручную.

Не путай `asyncio.Future` и `concurrent.futures.Future`: идеи похожи, но классы принадлежат разным моделям выполнения и не взаимозаменяемы напрямую.

## 42. `asyncio.gather()`

```python
async def main() -> None:
    results = await asyncio.gather(
        fetch_model(1),
        fetch_model(2),
        fetch_model(3),
    )
    print(results)
```

Операции выполняются конкурентно, а список результатов соответствует порядку переданных awaitable, не порядку фактического завершения.

По умолчанию исключение распространяется вызывающему коду. `return_exceptions=True` превращает исключения в элементы результата, что легко скрывает ошибку; используй только с явной обработкой каждого результата.

В Python 3.11 есть `TaskGroup`, обеспечивающий structured concurrency. Его сложные правила ошибок и отмены входят в отложенный Python Deep Dive; на этой неделе достаточно понимать назначение и уметь читать простой пример из документации.

## 43. Async queue

`asyncio.Queue` координирует producer и coroutine-workers внутри одного event loop:

- `await queue.put(item)`;
- `item = await queue.get()`;
- `queue.task_done()`;
- `await queue.join()`.

Как и в потоковой очереди, каждый `get()` требует `task_done()`. Остановка worker может выполняться sentinel-значениями. При этом `threading.Lock` для операций одной async-очереди не нужен: задача переключается только в точках await, но бизнес-инвариант всё равно нельзя разрывать неожиданным await между проверкой и изменением.

Продвинутые схемы backpressure, приоритетов, отмены и нескольких стадий pipeline отложены.

## 44. Блокирующий код рядом с asyncio

Если библиотека предоставляет только короткую блокирующую I/O-функцию, её можно вынести в thread:

```python
result = await asyncio.to_thread(blocking_io_function, argument)
```

Это не превращает библиотеку в нативно асинхронную и не является универсальным ускорением CPU-bound Python-кода. Сначала ищи async-совместимый клиент; `to_thread` полезен как мост для блокирующего I/O.

Нельзя вызывать `asyncio.run()` из уже работающего event loop. Внутри async-кода используй `await`.

## 45. Ошибки и порядок результатов

При конкурентном выполнении различай:

- порядок старта;
- порядок фактического завершения;
- порядок хранения итогового отчёта.

Порядок завершения недетерминирован. Тест не должен ожидать, что worker 1 всегда закончит первым. Для сравнения реализаций нормализуй результаты, например сортировкой по `task_id`.

Worker должен преобразовать ожидаемую ошибку в явный результат либо позволить coordinator получить исключение. Нельзя молча проглатывать ошибку и уменьшать число результатов.

Измерение времени также недетерминировано. Проверяй диапазон разумности только осторожно, а функциональные тесты основывай на данных, не миллисекундах.

## 46. Как выбрать модель выполнения

Задай вопросы:

1. Работа преимущественно ждёт I/O или считает на CPU?
2. Используемые библиотеки блокирующие или async-совместимые?
3. Сколько одновременно активных задач?
4. Нужна ли общая память?
5. Как будут передаваться ошибки и отмена?
6. Ограничен ли внешний сервис по частоте запросов?
7. Достаточен ли последовательный вариант?
8. Что показал профиль реальной нагрузки?

Начинай с простого корректного решения. Concurrency увеличивает число возможных порядков выполнения и стоимость отладки.

## 47. Архитектура итогового Task Dispatcher

```text
main.py
  создаёт одинаковый набор задач и запускает эксперименты
        |
        +--> sequential_runner.py
        +--> threaded_runner.py  --> queue.Queue + Thread workers
        +--> async_runner.py     --> asyncio.Queue + coroutine workers
        +--> process_runner.py   --> ProcessPool для CPU batch
        |
        +--> benchmarks.py       --> повторяемые измерения и отчёт

models.py
  TaskSpec и TaskResult

workloads.py
  блокирующая I/O-имитация, async-имитация и CPU-функция
```

Все I/O-режимы получают логически одинаковые задачи и возвращают нормализованный `list[TaskResult]`. Отдельная process-демонстрация показывает CPU-bound выбор, но не обязана быть быстрее на маленьком входе или одном доступном ядре.

`main.py` является безопасной точкой запуска. Импорт модулей не создаёт threads/processes и не вызывает `asyncio.run()`.

## 48. Типичные ошибки недели

1. Big O называют точным временем.
2. Два последовательных цикла ошибочно считают `O(n²)`.
3. Скрытую сортировку или копирование не включают в оценку.
4. Бинарный поиск запускают на несортированных данных.
5. Срезы в рекурсивном алгоритме игнорируют при анализе памяти.
6. `pop(0)` используют как быструю очередь.
7. Heap считают полностью отсортированным списком.
8. Рекурсия не приближает вход к базовому случаю.
9. `getsizeof()` контейнера принимают за размер всего графа.
10. Один benchmark объявляют универсальным доказательством.
11. Оптимизируют без профиля.
12. Concurrency путают с parallelism.
13. GIL принимают за mutex бизнес-инварианта.
14. Потоки используют для pure-Python CPU-bound работы и ожидают линейное ускорение.
15. Worker exception не извлекают из Future.
16. Process worker объявляют локальной функцией.
17. Процессы запускают при импорте модуля.
18. Coroutine вызывают, но не await-ят.
19. `time.sleep()` блокирует event loop.
20. CPU-heavy цикл помещают в coroutine и ожидают переключения.
21. Тест зависит от порядка завершения.
22. Для скорости делают жёсткий assert по времени.
23. `task_done()` вызывают не для каждого `get()`.
24. Ошибочные задачи молча исчезают из отчёта.

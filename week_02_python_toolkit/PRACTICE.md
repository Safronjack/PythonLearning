# Практика недели 2

Статус: **заблокирована до завершения недель 0 и 1**.

## Правила сдачи

После активации выполняй один день и пиши: `Проверь день N недели 2`. Агент проверяет код, не изменяя его, и обновляет `ASSESSMENT.md`.

Общие требования:

- использовать только стандартную библиотеку;
- сохранять контракт функций понятным;
- не применять пустой `except`;
- не использовать изменяемые значения параметров по умолчанию;
- добавлять `assert` для чистых функций;
- не запускать CLI при импорте модуля;
- заполнять самооценку;
- не использовать конструкцию, которую ученик не может объяснить.

## День 1. Параметры, аргументы и контракт функции

Файл: `day_01_function_arguments.py`

Теория: главы 1–3.

### 1. Контракт

Реализуй функции:

```text
calculate_subtotal(price, quantity)
calculate_discount_amount(subtotal, discount_percent=0)
calculate_final_price(price, quantity, discount_percent=0)
```

Для каждой укажи аннотации, короткий docstring, допустимые значения и `ValueError` для нарушенного правила.

### 2. Способы вызова

Вызови `calculate_final_price`:

- только позиционными аргументами;
- только именованными;
- смешанно в допустимом порядке;
- со скидкой по умолчанию.

Ошибочные варианты оставь комментариями и подпиши ожидаемый `TypeError`.

### 3. Keyword-only

Сделай `discount_percent` keyword-only. Докажи, что понятный вызов работает, а передача скидки третьим позиционным аргументом вызывает ошибку.

### 4. `*args`

Создай функцию суммы произвольного числа выручек. Проверь ноль, один и несколько аргументов. Объясни, почему внутри получен tuple.

### 5. `**kwargs`

Создай функцию описания автомобиля с обязательной моделью и дополнительными именованными характеристиками. Она возвращает новый словарь и не изменяет переданные данные.

### 6. Распаковка при вызове

Вызови одну функцию через tuple с `*`, другую через dict с `**`. Проверь неизвестный ключ и повторную передачу одного параметра.

### 7. Изменяемое значение по умолчанию

Воспроизведи проблему общего списка между вызовами, объясни момент вычисления default и напиши безопасную версию через `None`.

### 8. Возврат и изменение

Сравни две функции: изменяющую переданный список и возвращающую новый. Имена/docstring должны честно сообщать поведение.

Проверить: нули, отрицательные значения, скидки 0 и 100, пустые `args`, повторные вызовы default-функции.

Критерий: контракт соответствует поведению, defaults безопасны, распаковка объяснима, расчётные функции не печатают.

## День 2. LEGB и замыкания

Файл: `day_02_scopes_closures.py`

Теория: главы 5–6 и 16.

### 1. LEGB-наблюдение

Создай одинаковое имя на global, enclosing и local уровнях. До запуска предскажи, какое значение вернёт внутренняя функция. Отдельно покажи встроенное имя, не перекрывая его в итоговом коде.

### 2. Локальное присваивание

Покажи, что присваивание внутри функции не меняет одноимённое глобальное значение. Затем намеренно воспроизведи `UnboundLocalError`, закомментируй ошибочный код и объясни причину.

### 3. Решение без `global`

Сделай счётчик продаж как функция `next_sales_count(current_count)`, получающая старое значение и возвращающая новое. Сравни с версией через `global` и объясни, почему явная передача проще для теста.

### 4. Фабрика скидок

```text
make_discount_calculator(discount_percent)
```

Она возвращает функцию, применяющую зафиксированную скидку к цене. Создай калькуляторы для 5%, 10% и 20% и проверь их независимость.

### 5. Closure со состоянием

Создай `make_call_counter()`, возвращающую функцию-счётчик через `nonlocal`. Два созданных счётчика должны хранить независимое состояние.

### 6. Позднее связывание

Создай функции в цикле для скидок 5, 10 и 15 процентов. Сначала воспроизведи неожиданный одинаковый результат, затем исправь фиксацией значения. Объясни, когда внешнее имя читается closure.

### 7. `is` и `==`

Сравни равные отдельные списки, alias и `None`. Покажи, почему интернирование строк/чисел нельзя использовать как правило программы.

Критерий: LEGB объясняется по шагам, `global` не используется в решении основной задачи, `nonlocal` применён только для enclosing state.

## День 3. Функции как объекты и декораторы

Файл: `day_03_decorators.py`

Теория: главы 4 и 7.

### 1. Function object

Сохрани функцию расчёта в переменной, положи две операции в словарь и вызови выбранную по строковому ключу. Объясни разницу `function` и `function()`.

### 2. Функция высшего порядка

Напиши `apply_to_prices(prices, operation)`, которая создаёт новый список результатов и не меняет исходный.

### 3. Первый декоратор

Создай `announce_call`, который печатает имя функции до и после вызова. Он должен вернуть исходный результат.

### 4. Универсальная обёртка

Wrapper должен поддерживать позиционные и именованные аргументы через `*args`, `**kwargs`.

Проверь на функции с нулём, одним и несколькими аргументами.

### 5. `functools.wraps`

Сравни `__name__` и `__doc__` без `wraps`, затем добавь его и зафиксируй результат.

### 6. Декоратор проверки результата

Создай декоратор, который вызывает функцию и вызывает `ValueError`, если полученный денежный результат отрицательный. Не меняй положительный результат.

### 7. Декоратор с параметром

Создай простой `repeat(times)`. Проверь 1 и 3 повторения. Отрицательный `times` должен быть отвергнут при создании декоратора или до выполнения wrapper — выбери и опиши контракт.

### 8. Порядок декораторов

Примени два простых декоратора к одной функции и до запуска предскажи порядок сообщений. Не добавляй больше двух слоёв.

Критерий: результат функции не теряется, metadata сохранена, аргументы передаются, побочный эффект декоратора понятен.

## День 4. Модули, пакет и исключения

Файлы: `day_04_modules_exceptions.py`, `day_04_helpers.py`.

Теория: главы 8–9 и 17.

### 1. Разделение

В `day_04_helpers.py` размести константу максимальной скидки и чистые функции расчёта/валидации. В основном файле импортируй модуль целиком и вызови функцию через имя модуля.

### 2. Варианты import

Продемонстрируй обычный import, import с alias и импорт конкретного имени. Wildcard import оставь только комментарием с объяснением запрета.

### 3. Защита точки входа

В helper временно добавь диагностический вывод импорта, а CLI-вызов оставь под `if __name__ == "__main__"`. Докажи, что импорт не вызывает `input()` и `main()`.

### 4. Пользовательское исключение

Создай `InvalidSaleError`, наследующий `ValueError`. Функция валидации должна отличать отсутствующее поле, неверный тип и нарушение диапазона понятными сообщениями.

### 5. Цепочка ошибок

Преобразуй строковую цену в число. При `ValueError` создай `InvalidSaleError` через `raise ... from error`. Один раз выведи traceback и найди обе причины.

### 6. Иерархия и порядок except

Покажи обработку `FileNotFoundError` раньше `OSError`. Не лови `Exception` для обычного пути выполнения.

### 7. `else`, `finally`, повторный `raise`

Создай отдельные маленькие эксперименты и объясни, когда выполняется каждый блок. В одном обработчике добавь контекст и повторно подними исходную ошибку.

### 8. Минимальное logging

Настрой logging только в `main()`. Запиши INFO об успешном расчёте и ERROR об отклонённой продаже. Не логируй вымышленные пароли, email или токены.

Критерий: импорт не запускает интерфейс, зависимости направлены понятно, исключения не скрываются, исходная причина сохранена.

## День 5. Iterable, iterator и generator

Файл: `day_05_iterators_generators.py`

Теория: главы 10–11.

### 1. Iterator вручную

Для list получи iterator через `iter()`, вызови `next()` до исчерпания, безопасно обработай `StopIteration`. Объясни, почему второй `list(iterator)` пуст.

### 2. Iterable против iterator

Проверь `iter(models) is models` и `iter(iterator) is iterator`. Объясни результат.

### 3. Generator function

Напиши `iter_affordable_cars(cars, max_price)`, которая лениво выдаёт подходящие словари. Вызов до первого `next()` не должен выполнять тело обработки.

### 4. Порядок выполнения

Добавь временные диагностические сообщения до первого `yield`, между `yield` и в конце. До запуска предскажи порядок, затем убери лишнюю диагностику.

### 5. Generator expression

Сравни list comprehension и generator expression для цен. Проверь тип, одноразовость и отсутствие `len()`.

### 6. Pipeline

Раздели обработку:

```text
iter_active_sales → iter_valid_quantities → iter_expensive_sales
```

Каждый generator принимает iterable и выдаёт записи дальше. Исходный список не меняется.

### 7. Частичное потребление

Через `next()` возьми один элемент, затем продолжи циклом. Покажи, что первый элемент не повторяется.

### 8. `yield from`

Объедини несколько групп продаж в один поток. Сначала реализуй вложенным циклом, затем через `yield from`.

Критерий: generator не строит скрытый полный список, исчерпание и ленивость объясняются, pipeline работает с любым iterable.

## День 6. Контекстные менеджеры, файлы, JSON и Decimal

Файл: `day_06_files_serialization.py`.

Данные: `data/day_06_sales.json`, `data/day_06_invalid.json`.

Теория: главы 12–15.

### 1. `pathlib`

Построй пути относительно `__file__`. Выведи имя, суффикс, родителя, `exists()` и `is_file()`. Программа должна работать при запуске из корня проекта.

### 2. Контекстный менеджер файла

Прочитай текстовый JSON через `with path.open(..., encoding="utf-8")`. После блока покажи значение `file.closed`. Не закрывай файл вручную внутри `with`.

### 3. JSON API

Продемонстрируй различия `load`/`loads` и `dump`/`dumps`. Сформируй красивую JSON-строку с `ensure_ascii=False` и `indent=2`.

### 4. Ошибки JSON

Отдельно обработай:

- отсутствующий файл;
- повреждённый JSON;
- корректный JSON неверной структуры.

Не превращай все случаи в пустой список.

### 5. Decimal

Преобразуй строковые цены в `Decimal`. Сравни `Decimal("0.1")` и `Decimal(0.1)`. Рассчитай скидку и округли до двух знаков с явно выбранным правилом.

### 6. Запись отчёта

Запиши небольшой JSON-отчёт в новую папку `output`. Decimal перед сериализацией преобразуй в строку. Не перезаписывай исходный файл.

### 7. Собственный context manager

Через `@contextmanager` создай контекст, печатающий начало и завершение именованной операции. Завершение должно сработать при намеренно вызванном исключении.

### 8. Pickle — только безопасный эксперимент

Сериализуй и десериализуй созданный тобой локальный простой объект в отдельном временном учебном файле. В комментарии объясни, почему нельзя загружать чужой pickle. Не добавляй бинарный файл как обязательный результат сдачи.

Критерий: ресурсы закрываются, пути независимы от cwd, ошибки различаются, JSON проверяется, деньги не создаются из float.

## День 7. Итоговый проект «Sales Pipeline»

Каталог: `day_07_sales_pipeline/`.

Теория: глава 18 и повтор остальных глав.

### Структура

```text
day_07_sales_pipeline/
├── __init__.py
├── main.py
├── calculations.py
├── validators.py
├── generators.py
├── io_utils.py
├── decorators.py
├── data/
│   └── sales.json
└── output/
    └── report.json          # создаётся программой
```

### Входные данные

Файл содержит корректные и ошибочные записи. `price` хранится строкой. Валидная запись должна иметь:

- уникальный положительный целый `id`;
- непустые `dealership`, `buyer`, `model`, `date`;
- положительный `Decimal` price;
- положительный целый `quantity`;
- логический `is_active`.

### Модули

`validators.py`:

- `InvalidSaleError`;
- проверка обязательных ключей;
- проверка типов и диапазонов;
- преобразование цены в `Decimal`;
- нормализованная копия записи без изменения исходной.

`generators.py`:

- ленивый перебор активных записей;
- ленивый пропуск/сбор невалидных записей;
- обнаружение повторного id;
- сохранение понятной причины отклонения.

`calculations.py`:

- общая выручка;
- выручка по модели;
- количество единиц по модели;
- выручка по автосалону;
- уникальные покупатели;
- рейтинг моделей по количеству, выручке и названию.

`io_utils.py`:

- построение путей относительно пакета;
- чтение JSON;
- запись отчёта с `Decimal` в строковом формате;
- явная UTF-8 кодировка.

`decorators.py`:

- один декоратор с `@wraps`, который логирует имя вызванной функции;
- сохранение аргументов и возвращаемого результата.

`main.py`:

- настройка logging;
- связывание этапов;
- обработка файловых/JSON ошибок на границе CLI;
- печать краткого итога;
- отсутствие запуска при импорте.

### Ожидания для корректных записей

Валидные исходные записи дают:

- общую выручку `314000.00`;
- `Camry`: 4 единицы и `123000.00`;
- `X5`: 2 единицы и `93000.00`;
- `A6`: 1 единица и `42000.00`;
- `Civic`: 2 единицы и `56000.00`;
- 4 уникальных покупателя;
- рейтинг: `Camry`, `X5`, `Civic`, `A6`.

Ошибочные записи не участвуют в агрегатах, но каждая попадает в раздел `rejected` с id, если он доступен, и конкретной причиной.

### Обязательные сценарии

1. Исходный файл: корректный отчёт и все причины отказа.
2. Пустой JSON-массив: нулевой отчёт.
3. Отсутствующий файл: понятная ошибка без ложного отчёта.
4. Повреждённый JSON: отдельная ошибка формата.
5. JSON object вместо array: ошибка структуры.
6. Отрицательная/нулевая цена.
7. Нулевая/строковая quantity.
8. Пропущенный ключ.
9. Повторный id.
10. Неактивная корректная продажа не участвует в агрегатах.
11. Импорт `calculations` не запускает `main`.
12. Запуск из корня проекта находит данные.
13. Повторный запуск предсказуемо обновляет report, не исходный файл.
14. В отчёте нет несериализуемого `Decimal`.

### Ограничения

- без внешних библиотек;
- без классов, кроме класса исключения;
- без database/Django;
- без `pickle` для входных данных;
- без float для денег;
- без wildcard imports и изменения `sys.path`;
- без `except:` и скрытия ошибок пустым списком;
- без чтения файла в `calculations`;
- без печати внутри чистых агрегаторов;
- без изменения исходных записей;
- без полного готового решения из интернета.

### Критерий приёмки

- структура пакета соблюдена;
- импорты предсказуемы;
- все 14 сценариев проверены;
- ошибки входа отделены от бизнес-валидации;
- Decimal корректен;
- generator используется по назначению;
- decorator сохраняет metadata и результат;
- ресурсы закрываются;
- отчёт JSON читаем и воспроизводим;
- ученик может объяснить поток данных от пути до результата.
